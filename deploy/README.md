# Развертывание SousChef AI: демо-стенд и пилот

Рабочая сборка на одном сервере: настоящий сервер и интерфейс. Один `compose.yml` разворачивается двумя способами,
разница — в `.env`:
- **демо-стенд** — демо-сеть из 12 ресторанов (docs/11) в своем дне и с ночным сбросом. Решение — Q16 (прототип по
  ссылке заморожен), сервер и домен — Q17. Настройка — `.env.example`, раздел «Первый запуск»;
- **пилот** — настоящая сеть с реальными выгрузками: «сегодня» — настоящий день, ночного сброса нет, у каждого
  человека свой вход. Настройка — `.env.pilot.example`, раздел «Пилот».

Пилот разворачиваем на отдельном сервере (или хотя бы на отдельной базе), не на демо-стенде. Пароль демо раздают
гостям, а сброс демо работает только там, где нет других сетей.

## Что внутри (`compose.yml`)

| Сервис | Что делает |
|--------|------------|
| `db` | PostgreSQL 16. Роли создаются при первом запуске (`infra/postgres/init-prod.sh`): владелец схемы и роль приложения под RLS, пароли из `.env` |
| `migrate` | Применяет миграции при каждом запуске и завершается; API и воркер стартуют после него |
| `backend` | API (uvicorn, 2 процесса), `FAI_ENV=prod` |
| `worker` | Пересчет находок после загрузок. Каждые 10 минут — «подметальщик»: запускает пересчет, чья задача потерялась, и закрывает прерванный. Ночью — удаление старых исходных файлов (03:37 по Москве) и, на демо-стенде, сброс демо-сети (03:07) |
| `redis` | Очередь фоновых задач |
| `web` | Caddy: HTTPS с сертификатом Let's Encrypt (получает и продлевает сам), рабочая сборка интерфейса, `/api` — на backend. Поток чата (SSE) проходит без буферизации |

Демо живет в своем дне: `DEMO_TODAY` (по умолчанию 20.10.2026). Поэтому данные не «стареют», и сценарий из
`docs/14-demo-scenario.md` проходится в любой день. Каждую ночь демо-сеть собирается заново
(`python -m app.cli reset-demo`): что бы посетители ни нажали, утром все как в первый день. Сброс пересобирает только
демо-сеть и отказывается работать, если в базе есть другая сеть, кроме демо и тестовой (`docs/15-test-kit.md`).

## Что нужно от сервера

- Linux с Docker и Docker Compose; 2 vCPU, 4 ГБ памяти, 20 ГБ диска.
- Открытые порты 80 и 443.
- DNS-запись домена (A-запись) указывает на сервер — без нее Caddy не получит сертификат.

## Первый запуск

```sh
git clone https://github.com/krayzienike-web/ai_system.git && cd ai_system/deploy
cp .env.example .env    # заполнить: домен, пароли (без кавычек), JWT_SECRET и CASHIER_KEY (openssl rand -hex 32)
docker compose up -d --build
docker compose run --rm worker python -m app.cli reset-demo   # демо-сеть: ~30 секунд
```

Открыть `https://<домен>`. Входы — `admin@demo.local`, `analyst@demo.local`, `director1@demo.local` …
`director3@demo.local` с паролем `DEMO_PASSWORD`. Эти данные передаются приглашенным лично: в рабочую сборку
их не встраиваем (проверка `check-bundle` в CI).

## Тестовая сеть: загрузить выгрузки руками

Чтобы пройти путь пилота до настоящих выгрузок: `docker compose run --rm worker python -m app.cli seed-test-network
--password '<свой пароль>'` создает пустую «Тестовую сеть» (входы `admin@test.local`, `director1@test.local` …; пароль —
свой, не `DEMO_PASSWORD`). Файлы
для нее — в `deploy/test-kit/`, порядок загрузки и что должно получиться — в `docs/15-test-kit.md`. Ночной сброс
демо тестовую сеть не трогает; начать заново — `seed-test-network --reset --password '…'`. Только для синтетических
файлов набора: настоящие данные пилота — в отдельной конфигурации без демо-календаря.

## Пилот

Отдельный сервер с теми же требованиями. Демо-сеть и тестовую сеть здесь не заводим.

```sh
git clone https://github.com/krayzienike-web/ai_system.git && cd ai_system/deploy
cp .env.pilot.example .env   # домен, пароли, JWT_SECRET и CASHIER_KEY — свои, не как на демо-стенде
docker compose up -d --build
docker compose run --rm worker python -m app.cli create-tenant \
  --name "<сеть>" --admin-email <email> --admin-name "<ФИО>"
```

Команда печатает пароль администратора УК **один раз**. Передайте его лично: при первом входе система попросит
придумать свой.

Дальше:
1. Администратор входит и загружает справочники, начиная с «Рестораны» (docs/04).
2. Оператор заводит остальных людей:
   ```sh
   docker compose run --rm worker python -m app.cli add-user --tenant "<сеть>" \
     --email <email> --name "<ФИО>" --role director --restaurant R01   # или hq_admin / hq_analyst без ресторана
   docker compose run --rm worker python -m app.cli list-users --tenant "<сеть>"
   ```
3. Человек ушел или потерял пароль:
   - `disable-user --email …` — отключить, все его входы закрываются сразу;
   - `reset-password --email …` — новый выданный пароль, все входы закрываются.

Что отличает пилот от демо-стенда:
- `DEMO_TODAY` пустой, поэтому «сегодня» — настоящий день в часовом поясе `TIMEZONE` (по умолчанию Москва), а
  ночного сброса нет;
- без `FAI_REDIS_URL` и `FAI_CASHIER_KEY` сервер не запускается (в `compose.yml` они заданы);
- API не запускается, если RLS для его роли базы не действует (суперпользователь, `BYPASSRLS`, владелец таблиц);
- контейнеры с кодом работают не от root;
- исходные файлы удаляются по сроку: с ошибками — через 7 дней, остальные — через 90 (docs/04, Q37).

## Бэкапы

Дамп базы снимает `db-backup.sh` внутри контейнера `db`, дампы ложатся в `deploy/backups/` на сервере. Хранятся 14
дней. Команда `check` восстанавливает последний дамп в отдельную базу, сверяет число таблиц и удаляет ее.

```sh
docker compose exec -T db db-backup.sh          # снять дамп сейчас
docker compose exec -T db db-backup.sh check    # проверить, что последний восстанавливается
```

По расписанию — cron на сервере (`crontab -e`), путь — к папке `deploy`:

```
17 2 * * *  cd /opt/ai_system/deploy && docker compose exec -T db db-backup.sh
47 2 * * 0  cd /opt/ai_system/deploy && docker compose exec -T db db-backup.sh check
```

`deploy/backups/` лежит на том же сервере. Копию стоит регулярно уносить с него (другой сервер, хранилище провайдера):
пропажа сервера унесет и базу, и дампы. Куда уносить, решаем с заказчиком (Q37).

## Обновление

```sh
git pull && docker compose up -d --build
```

**Обновление 11.11.2026 (боевая конфигурация, этап 8, шаг 7)** — до `up` добавьте в `.env` строку
`CASHIER_KEY=<openssl rand -hex 32>`, без нее `compose` не запустится. Еще три изменения:
- коды кассиров демо-сети станут другими, ночной сброс пересоберет их сам;
- входы прежних сессий закончатся, всем нужно войти заново;
- на демо-стенде ночной сброс включается сам, пока задан `DEMO_TODAY`.

Миграции применятся сами (`migrate`). Демо-сеть пересоберется ночью или сразу командой `reset-demo`.

**Обновление 12.11.2026 (агенты, единицы в выгрузках)** — в `.env` ничего добавлять не нужно. Миграции 0032 (сообщения
агентов) и 0033 (единицы в выгрузках) применятся сами. Чтобы «Помощник» сразу показал сообщения демо-сети, после
`up` выполните `docker compose run --rm worker python -m app.cli reset-demo`, не дожидаясь ночи.
После обновления, которое меняет `Caddyfile` (10.11.2026: лимиты размера запроса и заголовок CSP), проверьте, что
`web` запустился: `docker compose logs --tail 20 web` — без ошибок `Caddyfile`. В среде разработки нет Caddy,
поэтому конфигурацию проверяет только тест файла.

## Ассистент

Пока ключа Claude API нет (Q12), `AI_PROVIDER=off`, и чат отвечает по правилам. Чтобы включить модель:
задать в `.env` `AI_PROVIDER=claude` и `ANTHROPIC_API_KEY=...`, затем выполнить `docker compose up -d`. Каждый
вызов модели пишется в журнал `ai_runs`. Лимит — 100 вопросов на человека в день.

## Проверено и не проверено

- Проверено 12.11.2026 по этой инструкции на чистом клоне, в Docker на одной машине (`DOMAIN=localhost`):
  - `docker compose up -d --build`: образы собираются, `migrate` применяет миграции и завершается, API, воркер
    (6 задач, в том числе утренние агенты и ночной сброс), Redis и Caddy стартуют;
  - API и воркер работают от пользователя `app` (uid 10001), не от root;
  - Caddy отдает HTTPS (для `localhost` — своим сертификатом вместо Let's Encrypt), с заголовком CSP; HTTP
    перенаправляется на HTTPS; несуществующий файл в `/assets/` — 404;
  - `reset-demo` — за 40 секунд, в «Помощнике» сразу три сообщения; вход, перезагрузка страницы без повторного
    входа — в браузере;
  - `db-backup.sh` и `db-backup.sh check`, `seed-test-network`, `run-agents`.
- Проверено раньше: `docker compose config` с `.env` демо-стенда старого вида, с `.env.pilot.example` и без
  `CASHIER_KEY` (11.11.2026); смена выданного пароля и выход — в браузере на рабочей сборке.
- Не проверено: сертификат Let's Encrypt на настоящем домене (нужны сервер и DNS, Q17) и пилотный режим
  (`create-tenant`, `add-user`) в собранных образах — команды проверены тестами, не на стенде.
