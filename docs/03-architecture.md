# 03. Архитектура

## Принципы

1. **Модульный монолит**, а не микросервисы: один деплой, четкие границы модулей, их можно вынести позже.
2. **Расчеты отдельно от ИИ.** Детерминированный аналитический слой → структурированные findings → LLM-слой.
   LLM никогда не придумывает цифры и не пишет произвольный SQL к боевой БД.
3. **Канонная модель данных + адаптеры источников.** XLS-импорт сегодня, iiko/r_keeper API завтра —
   на те же таблицы.
4. **Безопасность по умолчанию:** изоляция тенантов и ресторанов в БД (RLS), аудит, человек утверждает действия ИИ.
5. **Воспроизводимость и наблюдаемость:** версии алгоритмов и промптов, лог каждого вызова LLM, eval-тесты.

  `core/ops/mart/ai` — при росте, не раньше;

- LLM Gateway, чат (SSE) и сводки — этапы 5–6, модулей `ai` и `digests` в коде еще нет.

## Стек (обоснование — в ADR)

| Слой | Выбор | Почему |
|------|-------|--------|
| Backend | Python 3.12, FastAPI, Pydantic v2, SQLAlchemy 2, Alembic | Лучшая экосистема для аналитики/ML/LLM; типизация; OpenAPI из коробки |
| Аналитика | Python + `Decimal` по фактам из Postgres; Polars — разбор файлов импорта | Сейчас движок читает факты и считает в Python, вся логика покрыта тестами. Агрегаты в SQL, Polars в движке и окно дат — при росте сети (архитектурное ревью, п. 15) |
| Прогноз | statsmodels / LightGBM (MVP+) | Начинаем с прозрачного baseline |
| БД | PostgreSQL 16 | RLS, JSONB, оконные функции, рекурсивные CTE для ТТК |
| Очередь | arq + Redis | Простые асинхронные фоновые задачи, без тяжести Celery |
| Frontend | React + TypeScript + Vite, TanStack Query и Router, Tailwind с собственными компонентами дизайн-системы, ECharts | Быстрая разработка дашбордов; таблицы и графики — свои компоненты (TanStack Table и shadcn/ui не понадобились) |
| Импорт XLS | Polars + fastexcel (calamine) | Скорость и надежность чтения Excel и CSV |
| Auth | Собственный JWT (access + refresh), argon2 | Просто для MVP; SSO (OIDC) позже без изменения модели ролей |
| LLM | Claude API (официальный Python SDK `anthropic`) за тонким `LLMGateway` | Лучшее качество tool use и рассуждений; модели — в [ADR 0005](adr/0005-llm-provider-abstraction.md) |
| Инфра | Docker Compose (dev и демо-стенд), GitHub Actions CI | Один `make up` — и всё работает |
| Качество | ruff, mypy, pytest (+ factory-данные), eslint, tsc, Playwright e2e | Стандарт |

## Модули backend

```
backend/app/
  core/          конфиг, БД-сессии, ошибки, периоды, слова для чисел; без зависимостей от модулей домена
  auth/          логин, токены, пароли
  tenancy/       тенанты, рестораны, роли, scope, RLS-контекст
  catalog/       товары, алиасы, единицы, поставщики, блюда, ТТК + версии
  imports/       шаблоны, парсинг, валидация, staging, публикация, отчеты об ошибках
  operations/    продажи, приходы, перемещения, списания, инвентаризации
  analytics/     факты, себестоимость, расход по ТТК, модули M1–M7, движок находок, сверка находок с данными
                 (логика и параметры — docs/12-analytics-engine.md)
  norms/         нормы сети: целевой фудкост, допустимые потери, справочник причин списания
  insights/      реестр findings, приоритизация, статусы
  experiments/   проверки: группы, запуск / отклонение, результат (замер DiD — в analytics)
  tasks/         задачи директорам, чек-листы, подтверждения
  reports/       отчеты и выгрузки
  overview/      данные экранов-обзоров: сеть, «Моя неделя», рестораны, счетчики, снимки KPI и недельный тренд
                 (ADR 0007: экран только показывает, расчет — здесь)
  chat/          «Спросить су-шефа» до подключения LLM: ответы по правилам, цифры из данных и в пределах прав
  digests/       (этап 6) сборка входных данных сводки, карта процессов, хранение версий сводок
  ai/            (этап 5) gateway, промпты (версионируемые), tools, chat, narrator, digest writer, evals
  worker.py      фоновый воркер arq: пересчет находок (`analytics/runs.py`)
```

Правило зависимостей: `api → service → repository`; модули общаются через сервисные интерфейсы,
`analytics` не знает про `ai`, `ai` читает только через публичные сервисы и семантический слой.
Сейчас правило соблюдается не везде: есть взаимные зависимости модулей, а API-модули импортируют чужие API.
До этапа 5 вводим import-linter с этими контрактами в CI (архитектурное ревью, п. 11).

## AI-слой

Четыре AI-функции в MVP, все — поверх результатов расчетов (подробно про сводку и чат — [08](08-director-digest-and-chat.md)):

1. **Narrator** — для каждого нового finding генерирует: заголовок, объяснение простым языком,
   вероятные причины, рекомендованное действие, вопросы директору. Вход — структурированный finding + evidence.
2. **Hypothesis generator** — по finding предлагает гипотезу эксперимента: изменение, тестовая группа,
   метрика, длительность, ожидаемый эффект. Опирается на **библиотеку плейбуков** (курируемые типовые меры),
   LLM выбирает и адаптирует — не изобретает с нуля.
3. **Digest writer** — пишет еженедельную сводку директора (и сводку сети для УК) по детерминированно собранному
   входу: карта процессов, пробелы, предложения улучшений из плейбуков, прогресс.
4. **Чат с ассистентом** — отвечает на вопросы через **инструменты** (tool use): `get_kpis`, `get_findings`,
   `get_consumption_variance`, `get_purchase_prices`, `compare_restaurants`, `get_stock_forecast`, `explain_finding`…
   Инструменты исполняются с правами текущего пользователя — директор физически не получит чужие данные.
   В MVP — без генерации SQL (это безопаснее и точнее); text-to-SQL по семантическому слою — позже.

**Защита от галлюцинаций:**
- в ответ подставляются только числа из результатов инструментов; пост-проверка: каждое число в тексте
  должно встречаться во входных данных (иначе — повторная генерация / пометка);
- structured output (JSON-схема) для narrator и hypothesis;
- все действия с последствиями (задачи, эксперименты) — только после подтверждения человеком;
- `AiRun` лог: версия промпта, модель, входы, выход, токены, стоимость, латентность;
- **evals**: на демо-сети с заложенными аномалиями проверяем recall детекторов и качество объяснений;
  запускаются в CI при изменении промптов.

**Данные, уходящие в LLM** — агрегаты и справочники, без персональных данных (передача в зарубежный LLM согласована).
Для будущего AI HR (персональные данные сотрудников, 152-ФЗ) вопрос провайдера нужно будет решить отдельно.

## Безопасность и роли

- `RoleAssignment(user, role, scope)`: `hq_admin`, `hq_analyst` → scope = тенант; `restaurant_director` → scope = один ресторан
  (модель допускает список — для будущей роли владельца нескольких точек).
- Проверка в API (зависимость FastAPI `require_permission`) **и** Row-Level Security в Postgres:
  на каждый запрос выставляются `app.tenant_id` и `app.restaurant_ids`; политики RLS фильтруют строки.
  Ошибка в коде endpoint'а не приводит к утечке.
- Матрица прав (MVP):

| Действие | УК | Директор |
|----------|----|----------|
| Видеть все рестораны, сравнение с сетью | ✔ поименно по каждому ресторану | только свой + **среднее по сети** (без данных конкретных точек) |
| AI-сводка | ✔ все + сводка сети | ✔ своя |
| Загружать данные | ✔ все | ✔ свои |
| Редактировать справочники и ТТК | ✔ | ✘ |
| Запускать / отклонять проверки (`experiments.launch`) | ✔ (администратор) | ✘ — видит их задачи |
| Ставить задачи любому ресторану (`tasks.assign`) | ✔ (администратор) | ✘ — берет задачи себе |
| Выполнять задачи и отчитываться (`tasks.execute`) | ✘ | ✔ свои |
| Оспаривать находки | ✘ | ✘ — директора исполняют (ADR 0006) |
| Записывать результат задачи или проверки | ✘ — только расчетный слой | ✘ |
| Чат с ИИ | ✔ по сети | ✔ по своим данным |

- Аудит всех изменений и утверждений; хранение исходных файлов импорта.

## Окружения и деплой

- `dev` — Docker Compose локально; `demo` — один VPS/ВМ с Compose (Yandex Cloud / Selectel), HTTPS, бэкапы.
- Секреты — через переменные окружения/secret manager, не в репозитории.
- CI (GitHub Actions): lint + typecheck + unit + интеграционные тесты на Postgres + сборка фронта; e2e на демо-данных.
