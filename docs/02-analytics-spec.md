# 02. Спецификация аналитики (AI-менеджер запасов)

**Принцип:** все цифры считает детерминированный расчетный слой (SQL/Python), покрытый тестами.
LLM ничего не считает — она объясняет, приоритизирует, формулирует гипотезы и отвечает на вопросы,
опираясь только на посчитанные значения. Обозначения: ресторан `r`, товар `i`, блюдо `m`, период `P`.

Каждый модуль выдает **Finding** со структурой:
`type, restaurant, object, period, metric, value, benchmark, deviation, effect_rub_month, confidence, evidence[]`.

---

## M1. Исполнение ТТК (фактический vs теоретический расход)

Периоды задаются **между двумя инвентаризациями** (иначе факт неизвестен).

- Теоретический расход: `T(r,i,P) = Σ_m Sales(r,m,P) × Norm(m,i,date)` — норма брутто из версии ТТК,
  п/ф раскрываются рекурсивно.
- Фактический расход: `A = Остаток_нач + Приход + Перемещения_вх − Перемещения_исх − Остаток_кон`
  (остатки — фактические по инвентаризациям).
- Документированные списания: `W(r,i,P)`.
- **Необъяснимое отклонение:** `U = A − T − W`;  `U% = U / T`;  `U₽ = U × Себестоимость(i)`.

Флаг, если одновременно:
- `|U%|` > допуска категории (например, овощи 3%, мясо 2%, напитки 1% — настраивается);
- `U₽` > порога существенности;
- отклонение выбивается из сети: `z = (U%_r − median_сети) / MAD_сети > 2` (robust z-score по ресторанам).

Интерпретация для ИИ: перерасход → нарушение ТТК/выход, хищение, неучтенные списания, ошибка ТТК;
экономия (U < 0) → недовложение (риск качества!), неучтенный приход, ошибка ТТК.
Если **все** рестораны сети дают одинаковое отклонение по товару — вероятнее ошибка ТТК, а не ресторана.
Это важный инсайт для УК («обновите ТТК»).

## M2. Фудкост

- Себестоимость товара: средневзвешенная по приходам (MVP), FIFO — позже.
- `FC_теор% = Σ_i T × C / Выручка_нетто`;   `FC_факт% = Σ_i A × C / Выручка_нетто`.
- **Gap = FC_факт − FC_теор** (п.п.) → `₽ = Gap × Выручка`. Разложение gap по товарам (из M1) и по причинам:
  отклонения ТТК, списания, рост цен.
- По блюдам: себестоимость порции по текущим ценам, маржа, динамика. Флаг: блюдо, у которого
  FC% вырос > X п.п. из-за цены ингредиента → рекомендация пересмотра цены/ТТК.
- (MVP+) Меню-инжиниринг (матрица Kasavana–Smith: популярность × маржа) — те же данные, высокий «вау» для демо.

## M3. Контроль закупочных цен

Цена приводится к базовой единице. Для каждой строки прихода считаются бенчмарки:
1. Собственная медиана ресторана за 4 недели (скачок цены);
2. Медиана сети по товару за ту же неделю (переплата относительно других точек);
3. Контрактная цена (если загружен прайс/договор);
4. Лучшая цена в сети за период.

- **Переплата:** `Overpay = (p − benchmark) × qty`, агрегируется в ₽/мес по ресторану, поставщику, товару.
- Флаги: скачок > X% к собственной медиане; цена > медианы сети на > Y%; один поставщик продает разным точкам по разным ценам;
  цена выше контрактной; дробление закупок у «дорогого» поставщика при наличии дешевого.
- Эффект для гипотезы: «перевести закупку товара i на поставщика S / договориться о цене» = Overpay × 12.

## M4. Контроль инвентаризаций

- **Регулярность:** частота, пропуски регламента, покрытие (% номенклатуры в пересчете, % по стоимости).
- **Результаты:** недостачи/излишки ₽ и % от оборота, тренд, сравнение с сетью.
- **Подозрительные паттерны** (сигнал низкого качества или манипуляции):
  - систематически нулевые расхождения («пересчет на бумаге»);
  - пересорт: излишек и недостача близких товаров примерно на одну сумму;
  - излишек в одной инвентаризации, недостача той же величины в следующей;
  - всплеск списаний за 1–2 дня до инвентаризации;
  - «круглые» фактические остатки.
- **Индекс дисциплины инвентаризаций** (0–100) на ресторан — для рейтинга.
- Влияние на уверенность: без регулярных инвентаризаций M1/M2 работают с пониженной `confidence`.

## M5. Контроль списаний

- Списания ₽ и % выручки по причинам, ресторанам, товарам; сравнение с сетью.
- Аномалии: всплеск к собственной истории (сезонно-скорректированный), списания дорогих позиций,
  повторяющиеся списания одного товара (проблема заказа/хранения → связь с M6).
- Порча из-за перезаказа: товар часто списывается и при этом часто заказывается «впрок» → гипотеза уменьшить партию.

## M6. Прогноз дефицита и рекомендация заказа

1. Прогноз продаж блюд по дням. MVP: сезонно-наивный (среднее по тому же дню недели за 4–6 недель × тренд) —
   прозрачно и надежно. MVP+: градиентный бустинг/Prophet с праздниками и погодой. Метрика качества — WAPE на бэктесте.
2. Потребность в товаре = прогноз продаж × ТТК (+ средний уровень списаний).
3. Расчетный остаток = последний фактический остаток + движения после него.
4. **Дни покрытия** = остаток / среднесуточная потребность; **дата обнуления**.
5. Риск: дата обнуления раньше ближайшей поставки (график поставок/lead time поставщика) → красный.
6. **Рекомендованный заказ** = потребность на (lead time + период до следующей поставки) + страховой запас − остаток − в пути.
   Страховой запас = `z × σ_спроса × √lead_time`.
7. Обратная сторона — **затоваривание**: дни покрытия > срока годности или > N дней → замороженные деньги и риск порчи.

Эффект: упущенная выручка от стоп-листа (продажи блюд × маржа за дни дефицита) и стоимость затоваривания.

## M7. Качество данных

Отдельный модуль, потому что без него аналитика производит ложные инсайты.
Проверки: продаваемые блюда без ТТК; товары без конверсии единиц; отрицательные расчетные остатки;
нулевые/аномальные цены; несопоставленные названия товаров; пропуски дней продаж; инвентаризации без части товаров.
Итог — **Data Quality Score** по ресторану, влияющий на `confidence` всех его инсайтов.

## Финансовый эффект и приоритизация

- Единица эффекта — **₽/месяц** (и годовая экстраполяция для презентации).
- Консервативность: эффект считается до бенчмарка сети (медианы), а не до идеала. Это правдоподобно и защищаемо перед инвестором.
- **Потенциал тиражирования:** если проблема найдена в 1 ресторане, а аналогичная картина в других — эффект «на сеть».
- **Приоритет** = эффект₽ × confidence × легкость_исправления (из библиотеки плейбуков).
- Сумма по всем открытым инсайтам — **«деньги на столе»**, главный KPI на дашборде УК.

## Пересчет

Расчеты идут пакетно после каждой загрузки (фоновая задача): витрины → метрики → детекторы → findings →
LLM-обогащение новых findings. Повторный расчет идемпотентен: обновляет findings по ключу (тип, ресторан, объект, период).
