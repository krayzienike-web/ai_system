# 09. Требования к данным

Какие данные нужны, в каком виде и откуда их взять в **iiko**, **r_keeper** и **1С:ERP**.
Конкретные названия отчетов ориентировочные — точная настройка будет по реальным выгрузкам.
Система **адаптируется к формату файла** (см. «Адаптивный импорт» ниже), поэтому подгонять файлы под шаблон вручную не нужно.

## Минимальный объем для пилота

- **3 ресторана × не менее 3 месяцев** истории (лучше 6 — для сезонности и прогноза).
- **Не менее 3 инвентаризаций на ресторан** за этот период (полных или хотя бы по ключевым позициям).
  Без инвентаризаций фактический расход неизвестен → модули ТТК и фактического фудкоста не работают.
- Дальше — регулярная загрузка раз в неделю (продажи, приходы, списания, перемещения) и после каждой инвентаризации.

## Где взять в учетных системах (ориентировочно)

| Набор | iiko (iikoOffice) | r_keeper (+ StoreHouse) | 1С:ERP |
|-------|-------------------|-------------------------|--------|
| Номенклатура | Справочник номенклатуры (экспорт) | StoreHouse: справочник товаров | Справочник «Номенклатура» |
| Блюда | Номенклатура (тип «Блюдо») | r_keeper: справочник блюд (меню) | Номенклатура (продукция) |
| ТТК | Технологические карты (отчет/экспорт) | StoreHouse: калькуляционные карты | Ресурсные спецификации |
| Продажи | OLAP-отчет по продажам (день × блюдо) | Отчеты r_keeper по продажам блюд | Отчеты о розничных продажах |
| Приходы | Приходные накладные / OLAP по проводкам | StoreHouse: приходные накладные | Поступление товаров и услуг |
| Инвентаризации | Документы инвентаризации | StoreHouse: инвентаризационные описи | Пересчет товаров, оприходование излишков / списание недостач |
| Списания | Акты списания | StoreHouse: расходные накладные / списания | Внутреннее потребление, списание товаров |
| Перемещения | Внутренние перемещения | StoreHouse: внутренние перемещения | Перемещение товаров |
| Остатки | Остатки на складах / оборотно-сальдовая ведомость | StoreHouse: остатки | Ведомость по товарам на складах |

Формат выгрузки: XLSX или CSV, «плоская» таблица (одна строка = одна запись), без объединенных ячеек.
Если отчет выгружается только «красивым» (с шапкой, итогами, группировками) — тоже подходит:
парсер умеет пропускать шапку и строки итогов, это настраивается в профиле источника.

## Связка данных из разных систем

Если у одного ресторана продажи в r_keeper, а склад и ТТК в 1С (или наоборот), коды блюд и товаров в системах разные.
Решение — таблица соответствий (`ProductAlias` / `MenuItemAlias`), которая заполняется автоматически
(точное совпадение → нечеткое → предложение ИИ) и подтверждается человеком один раз.

## Адаптивный импорт

Модель данных не требует, чтобы файлы совпадали с нашими шаблонами:

1. **Профиль источника** — для каждого типа отчета каждой системы (например, «iiko · OLAP продажи») хранится
   маппинг колонок, правила пропуска шапки и итогов, формат дат и чисел, единицы.
2. **Автораспознавание** — при первой загрузке колонки распознаются по словарю синонимов и ИИ (по заголовкам и
   образцу строк); человек подтверждает предпросмотр, профиль сохраняется, дальше применяется автоматически.
3. **Ничего не теряем** — колонки, которых нет в модели, сохраняются в поле `extra` (JSONB) и могут стать полями позже без повторной загрузки.
4. **Изменился формат** (добавили колонку, переименовали) — система замечает расхождение с профилем и предлагает обновить маппинг, а не падает.
5. Тот же профиль-подход будет использован для API-интеграций: адаптер пишет в те же staging-таблицы.

## Персональные данные

Для модуля запасов ПДн не нужны. Если в выгрузках есть ФИО (например, ответственный за списание) — при импорте
они не сохраняются или псевдонимизируются. В LLM уходят только агрегаты и справочники.
