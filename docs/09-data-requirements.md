# 09. Требования к данным

Какие данные нужны, в каком виде и откуда их взять в **iiko**, **r_keeper** и **1С:ERP**.
Конкретные названия отчетов ориентировочные — точная настройка будет по реальным выгрузкам.
Система **адаптируется к формату файла** (см. «Адаптивный импорт» ниже), поэтому подгонять файлы под шаблон вручную не нужно.

## Источники в пилоте

| Данные | Система |
|--------|---------|
| Продажи (блюда, выручка, скидки) | **r_keeper** |
| Номенклатура, ТТК, остатки, инвентаризации, списания, перемещения (склад) | **iiko** |
| Закупки: поставщики, накладные, цены | **1С:ERP** |

Следствия:
- **Связка кодов между системами** обязательна: блюда r_keeper ↔ блюда/ТТК iiko, товары 1С:ERP ↔ товары iiko.
  Заполняется автоматически (код → название → ИИ) с подтверждением человеком один раз.
- **Закупки в ERP и оприходование в iiko.** Приходы вводятся в обеих системах: количество для движения запасов берем
  из iiko, а цены и поставщиков — из ERP. Расхождение «закуплено в ERP, но не оприходовано в iiko» — отдельная проверка
  и сильный сигнал (потери при приемке или учете).

## Минимальный объем для пилота

- **3 ресторана × 6 месяцев** истории. Инвентаризации проходят раз в 1–3 месяца, а для фактического расхода
  нужен период между двумя пересчетами, поэтому меньший срок может не дать ни одного закрытого периода.
- **Не менее 2 полных инвентаризаций на ресторан** (лучше 3+) за этот период.
- Дальше — загрузка раз в неделю (продажи, закупки, списания, перемещения) и после каждой инвентаризации.

## Где взять в учетных системах (ориентировочно)

| Набор | iiko (iikoOffice) | r_keeper (+ StoreHouse) | 1С:ERP |
|-------|-------------------|-------------------------|--------|
| Номенклатура | Справочник номенклатуры (экспорт) | StoreHouse: справочник товаров | Справочник «Номенклатура» |
| Блюда | Номенклатура (тип «Блюдо») | r_keeper: справочник блюд (меню) | Номенклатура (продукция) |
| ТТК | Технологические карты (отчет/экспорт) | StoreHouse: калькуляционные карты | Ресурсные спецификации |
| Продажи | OLAP-отчет по продажам (день × блюдо) | Отчеты r_keeper по продажам блюд | Отчеты о розничных продажах |
| Приходы | Приходные накладные / OLAP по проводкам | StoreHouse: приходные накладные | Поступление товаров и услуг |
| Инвентаризации | Документы инвентаризации | StoreHouse: инвентаризационные описи | Пересчет товаров, оприходование излишков / списание недостач |
| Списания | Акты списания | StoreHouse: расходные накладные / списания | Внутреннее потребление, списание товаров |
| Перемещения | Внутренние перемещения | StoreHouse: внутренние перемещения | Перемещение товаров |
| Остатки | Остатки на складах / оборотно-сальдовая ведомость | StoreHouse: остатки | Ведомость по товарам на складах |
| Удаления и отмены | — | r_keeper: отчет по удалениям / отказам (с кассиром и статусом пречека) | — |

Формат выгрузки: XLSX или CSV, «плоская» таблица (одна строка = одна запись), без объединенных ячеек.
Если отчет выгружается только «красивым» (с шапкой, итогами, группировками) — тоже подходит:
парсер умеет пропускать шапку и строки итогов, это настраивается в профиле источника.

## Связка данных из разных систем

Если у одного ресторана продажи в r_keeper, а склад и ТТК в 1С (или наоборот), коды блюд и товаров в системах разные.
Решение — таблица соответствий (`NameAlias`: товары, блюда, поставщики), которая заполняется автоматически
(точное совпадение → нечеткое → предложение ИИ) и подтверждается человеком один раз.

## Адаптивный импорт

Модель данных не требует, чтобы файлы совпадали с нашими шаблонами:

1. **Профиль источника** — для каждого типа отчета каждой системы (например, «iiko · OLAP продажи») хранится
   маппинг колонок, правила пропуска шапки и итогов, формат дат и чисел, единицы.
2. **Автораспознавание** — при первой загрузке колонки распознаются по словарю синонимов и ИИ (по заголовкам и
   образцу строк); человек подтверждает предпросмотр, профиль сохраняется, дальше применяется автоматически.
3. **Ничего не теряем** — колонки, которых нет в модели, сохраняются в поле `extra` (JSONB) и могут стать полями позже без повторной загрузки.
4. **Изменился формат** (добавили колонку, переименовали) — система замечает расхождение с профилем и предлагает обновить маппинг, а не падает.
5. Тот же профиль-подход будет использован для API-интеграций: адаптер пишет в те же staging-таблицы.

Сделано на этапе 5.5 (`imports.SourceProfile`, `/imports/mapping`, ADR 0008):
1. Незнакомый файл, у которого не нашлась строка заголовков, на экране загрузки можно «Разметить с ИИ».
2. Строку заголовков находит код, ИИ видит заголовки и пять строк-образцов.
3. Импорт сразу проверяет разметку на самом файле и показывает, сколько строк читается и сколько с ошибками.
4. После подтверждения разметка становится профилем: директор подтверждает для своего ресторана, УК — для всей
   сети. Следующие файлы с такими заголовками загружаются без шаблона и без ИИ, со всеми проверками импорта.
   Синонимы шаблона важнее профиля, конфликтующий профиль не сохраняется, неверный профиль можно удалить.
5. Изменившийся формат («добавили колонку»): загрузка не падает, файл можно разметить заново, модель спрашивают
   только о новой колонке.

Чего из описанного выше пока нет (бэклог):
- в профиле — только соответствие колонок; правил шапки и итогов, форматов дат и чисел нет (их берет общий разбор
  файла);
- поля `extra` для колонок вне модели нет: исходный файл целиком хранится в `import_batches.raw`.

## Персональные данные

Для модуля запасов ПДн не нужны. Если в выгрузках есть ФИО (например, ответственный за списание) — при импорте
они не сохраняются или псевдонимизируются. В LLM уходят только агрегаты и справочники. Исходные файлы, где ФИО
еще есть, удаляются по сроку: 7 дней для файлов с ошибками, 90 — для остальных ([04](04-data-import.md), Q37).

**Кассиры** (продажи, удаления и отмены — этап 6.5): код или табельный номер целиком («таб. 104», «№ 17», «K12») сохраняется как есть;
все остальное (в том числе ФИО с цифрами) считается ФИО и заменяется устойчивым кодом «Кассир XXXXXXXX». Код — HMAC-SHA256
от сети и имени на секретном ключе сервера `FAI_CASHIER_KEY` (ревью перед пилотом, п. 19): у одного человека в сети
всегда один код, имя не хранится, в другой сети код другой. Без ключа нельзя узнать, чей это код, перебирая имена;
ключ задают один раз и не меняют, иначе у всех кассиров появятся новые коды. Находки по кассе называют кассира этим значением. Как УК удобнее узнавать кассира — вопрос Q26.
