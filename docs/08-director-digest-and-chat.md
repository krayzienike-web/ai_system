# 08. AI-сводка директора и чат с AI-ассистентом

Две функции, которые делают продукт полезным **директору**, а не только УК. Директор получает не «надзор»,
а персонального аналитика: где в его процессах пробелы, сколько это стоит и что конкретно сделать.

---

## Часть 1. AI-сводка директора

### Цель
Раз в неделю (и по запросу) показать директору: какие процессы ресторана работают хорошо, где по данным видны
пробелы, сколько это стоит в ₽ и какие улучшения предлагаются. Тон — коуч, не контролер.

### Карта процессов

Каждый сигнал аналитики привязан к процессу ресторана. Сводка показывает процессы, а не «таблицу отклонений».

| Процесс | Сигналы из данных (модули [02](02-analytics-spec.md)) | Пример пробела |
|---------|------------------------------------------------------|----------------|
| **Закупка** | M3: переплаты, скачки цен, дорогой поставщик | «Сливки берете на 14% дороже двух других точек» |
| **Приемка** | M1/M4: систематические недостачи сразу после поставок, расхождение кол-ва в накладной и факта | «Недостача курицы в дни поставок — проверка веса при приемке?» |
| **Хранение** | M5: порча по скоропорту, списания по срокам | «Зелень списывается каждую неделю — партия больше потребления» |
| **Производство (ТТК)** | M1: перерасход/недовложение, M2: gap фудкоста | «Перерасход сыра 9% при допуске 2% — порционирование на раздаче» |
| **Списания** | M5: всплески, причины, списания перед инвентаризацией | «60% списаний оформлено в последний день перед пересчетом» |
| **Инвентаризация** | M4: регулярность, покрытие, подозрительные паттерны | «3 пересчета подряд с нулевым расхождением по 40 позициям» |
| **Учет и данные** | M7: блюда без ТТК, ошибки единиц, пропуски | «12 продаваемых блюд без ТТК — фудкост по ним не считается» |
| **Планирование запасов** | M6: риск дефицита, затоваривание | «Через 3 дня закончится моцарелла, поставка через 5» |

Каждому процессу — статус (норма / внимание / проблема), индекс 0–100 и тренд к прошлой неделе.

### Структура сводки

1. **Главное за неделю** — 2–3 предложения от ИИ.
2. **Ключевые показатели** — фудкост факт / теория, необъяснимые отклонения ₽, списания ₽ и %, переплаты ₽;
   сравнение с прошлой неделей и **со средним по сети** (данные конкретных точек директору не показываются).
3. **Карта процессов** — светофор по 8 процессам.
4. **Проблемы: где теряем деньги (3–5)** — то, что надо исправить. Для каждой: что видно в данных,
   **сколько теряем (₽/мес)**, доказательство (график/строки), вероятные причины, что сделать.
   Примеры: перерасход по ТТК, переплата поставщику, списания выше нормы, недостачи при инвентаризации.
5. **Возможности: что улучшить и сколько заработать (3–5)** — то, что работает «нормально», но может работать лучше.
   Для каждой: идея, **потенциал (₽/мес)**, на чем основан расчет, сложность внедрения.
   Примеры: перейти на лучшую цену сети по позиции, пересмотреть цену блюда с выросшей себестоимостью,
   уменьшить партию скоропорта, выйти на уровень списаний среднего по сети.
   Для проблем и возможностей одинаковые кнопки: **«Беру в работу»** (задача директора самому себе),
   **«Не согласен»** (с причиной), **«Обсудить с ИИ»** (чат с контекстом пункта).
6. **Итог «на столе»**: сумма потерь + сумма потенциала, ₽/мес.
7. **Что улучшилось** — прогресс по прошлым задачам и выросшие индексы (позитивное подкрепление).
8. **Риски на ближайшие дни** — дефициты и затоваривание (M6).

Правило отбора: в каждый блок попадает 3–5 пунктов с наибольшим `эффект × уверенность`; пунктов меньше 3 —
блок показывает сколько есть, без «натягивания». Проблема и возможность по одному объекту не дублируются.

**Учет редких инвентаризаций (раз в 1–3 месяца):** фактический расход по ТТК и недостачи пересчитываются только
после инвентаризации. Еженедельная сводка между пересчетами опирается на то, что меняется каждую неделю
(цены закупок, списания, теоретический фудкост, дефициты, качество данных), а блок «ТТК / недостачи» показывает
результаты последней инвентаризации с датой. Сводка после инвентаризации — расширенная.

### Как формируется

```
после загрузки данных за неделю / по расписанию / по кнопке
  → DigestBuilder (детерминированно): собирает метрики, индексы процессов, findings, задачи → digest_input.json
  → LLM (structured output по JSON-схеме разделов): тексты, формулировки, приоритизация предложений
  → проверка: все числа в тексте присутствуют в digest_input; иначе — повторная генерация
  → Digest(restaurant, period, version, input, output) → UI + email
```

- УК видит сводки всех ресторанов и **сводку сети** (тот же механизм, уровень — сеть).
- Отчеты директоров о выполнении задач и измеренный результат копятся и используются для настройки допусков и плейбуков (оспаривания нет — [ADR 0006](adr/0006-tasks-execution-and-traceability.md)).
- Каналы: в приложении + email. Telegram — после MVP.

## Часть 2. Чат с AI-ассистентом

### Цель
Любой вопрос к данным на естественном языке — ответ с цифрами, таблицей или графиком и ссылкой на источник.

### Примеры вопросов

- Директор: «Почему вырос фудкост на прошлой неделе?», «Какие позиции я переплачиваю?»,
  «Что закончится до следующей поставки?», «Покажи отклонения по ТТК за месяц по мясу», «Как мне снизить списания зелени?»
- УК: «Сравни три ресторана по фудкосту за квартал», «У кого самые нерегулярные инвентаризации?»,
  «Сколько сеть переплачивает поставщику X?», «Какие эксперименты дали эффект?»

### Как устроен

- **Tool use**: модель не видит базу напрямую, а вызывает инструменты расчетного слоя.
  Инструменты выполняются **с правами текущего пользователя** (директор технически не получит данные другой точки).

| Инструмент | Что возвращает |
|-----------|----------------|
| `get_kpis(period, restaurant?)` | Фудкост, списания, отклонения, переплаты |
| `get_consumption_variance(period, product?/category?)` | Теория / факт / списания / отклонение по товарам (M1) |
| `get_food_cost(period, by=dish/category)` | Фудкост и маржа (M2) |
| `get_purchase_prices(product?, supplier?, period)` | Цены, бенчмарки, переплаты (M3) |
| `get_inventory_quality(period)` | Индекс дисциплины, расхождения, паттерны (M4) |
| `get_write_offs(period, reason?)` | Списания (M5) |
| `get_stock_forecast(horizon_days)` | Остатки, дни покрытия, риски дефицита (M6) |
| `get_data_quality()` | Проблемы данных (M7) |
| `get_findings(status?, process?)` / `explain_finding(id)` | Инсайты с evidence |
| `compare_restaurants(metric, period)` | Поименное сравнение ресторанов — только УК |
| `get_network_average(metric, period)` | Среднее по сети — доступно директору (только агрегат) |
| `get_digest(period)` / `get_tasks()` / `get_experiments()` | Сводки, задачи, эксперименты |
| `search_products(query)` | Поиск товара/блюда по названию (нечеткий) |

- **Формат ответа**: текст + блоки «таблица» и «график» (инструменты возвращают данные, фронт рисует) +
  «откуда цифра» (ссылка на finding/отчет) + 2–3 предложенных следующих вопроса.
- **Контекст**: чат открывается из инсайта, сводки или задачи — с уже подставленным объектом обсуждения.
- **Действия** только как черновики с подтверждением человеком: «создать задачу», «предложить гипотезу УК».
- **Честность**: нет данных → так и говорит («инвентаризаций за период нет, факт не посчитать»), не выдумывает.
- **Технически**: Claude API, стриминг ответа (SSE), кэширование системного промпта и описаний инструментов
  (prompt caching), история диалогов в БД, лимиты на пользователя, лог каждого вызова в `AiRun`.

### Качество

- Eval-набор: ~50 вопросов к демо-сети с эталонными ответами; проверяем правильность выбора инструментов,
  совпадение чисел, соблюдение прав (директор спрашивает про чужую точку → отказ). Запускается в CI при изменении промптов.
- Оценка в интерфейсе (👍/👎 + комментарий) → разбор плохих ответов.
