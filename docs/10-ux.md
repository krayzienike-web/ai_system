# 10. UX: разбор текущего интерфейса и целевая концепция

> Заменен документами [docs/ux/](ux/): аудит, бренд и дизайн-система, To-Be. Оставлен как история решений.

## 1. Разбор текущего каркаса (этап 1)

Каркас технический: проверяет вход, роли и изоляцию, но как продукт пока ничего не дает. Проблемы:

| # | Проблема | Почему важно | Серьезность |
|---|----------|--------------|-------------|
| U1 | **Телефон не работает.** Боковое меню занимает половину экрана 390px, текст ломается в столбик | Директор ресторана в зале и на кухне, а не за компьютером — основной его экран телефон | Высокая |
| U2 | **Навигация по модулям системы, а не по задачам человека.** 7 пунктов, из них 6 «скоро» — тупики | Пользователь видит структуру продукта, а не ответ «что мне делать» | Высокая |
| U3 | **Главная пустая.** Первый экран не отвечает ни на один вопрос | Ценность должна быть видна за 5 секунд — особенно на демо инвестору | Высокая |
| U4 | **Директору показаны лишние разделы** («Эксперименты») | Директор не управляет экспериментами, он получает задачи | Средняя |
| U5 | **Нет контекста данных:** за какой период, когда обновлено, когда последняя инвентаризация | Без этого цифрам не доверяют; при инвентаризациях раз в 1–3 мес это критично | Средняя |
| U6 | **ИИ спрятан в отдельный пункт «Чат»** | Вопрос возникает у конкретной цифры — ИИ должен быть рядом с ней | Средняя |
| U7 | Дублирование «Администратор УК / Администратор УК», мелкая серая метка «скоро» (10px, низкий контраст) | Мелочи, но снижают ощущение качества | Низкая |
| U8 | Вход: нет «показать пароль», «забыли пароль», нет подсказки демо-доступа | Демо и первые пользователи | Низкая |

## 2. Принципы

1. **Действие первым.** Любой экран отвечает по порядку: *сколько теряем → почему → что сделать → кнопка*.
2. **Рубли — главная единица.** Эффект всегда в ₽/мес, одинаковый формат («112 тыс ₽/мес»). Проценты — вторично.
3. **Каждой цифре — «откуда».** Период, источник, свежесть данных, уверенность. Любая цифра раскрывается
   до исходных строк (накладная, акт списания, инвентаризация).
4. **Постепенное раскрытие.** Сводка → карточка проблемы → доказательство → исходные строки. Не вываливать таблицы на главную.
5. **ИИ — в контексте.** Кнопка «Обсудить с ИИ» на каждой карточке открывает чат с уже подставленным объектом;
   общий чат — выдвижная панель на любом экране, а не отдельная страница.
6. **Сначала компьютер, телефон — адаптив.** Большинство пользователей (и директора, и УК) работают с ПК; на телефоне все экраны должны оставаться удобными (меню-«бургер», карточки в одну колонку).
7. **Честность данных.** Если данных не хватает — так и говорим и подсказываем, что сделать
   («Нужна вторая инвентаризация, чтобы посчитать потери по ТТК. Следующая — по графику 01.11»).
8. **Тон коуча, не надзирателя** (для директора): «что улучшилось» на видном месте, формулировки без обвинений.

## 3. Информационная архитектура

### Директор (боковое меню на ПК, «бургер» на телефоне)

| Вкладка | Что внутри |
|---------|------------|
| **Сводка недели** (главная) | AI-сводка: итог в ₽, карта процессов, проблемы, возможности, риски дефицита, что улучшилось |
| **Задачи** | Мои задачи (из сводки и от УК), сроки, отметка выполнения с фото/комментарием |
| **Ассистент** | Чат с ассистентом, подсказки вопросов |
| **Данные** | Загрузка выгрузок, свежесть данных своего ресторана |

### Управляющая компания (desktop, боковое меню)

| Раздел | Что внутри |
|--------|------------|
| **Обзор сети** (главная) | «Деньги на столе» по сети, рестораны × процессы (тепловая карта), главные инсайты, эксперименты в работе, просроченные задачи |
| **Инсайты** | Реестр проблем и возможностей с фильтрами (ресторан, процесс, вид, статус), сортировка по ₽ |
| **Эксперименты** | Гипотезы на утверждение, идущие эксперименты, результаты |
| **Задачи** | Контроль исполнения по ресторанам |
| **Рестораны** | Карточка ресторана = «взгляд директора» + поименное сравнение |
| **Данные** | Загрузки, свежесть данных по источникам и ресторанам, качество данных |
| **Настройки** | Пользователи, нормативы (допуски потерь, целевой фудкост), плейбуки |

Чат с ИИ — выдвижная панель справа на любом экране (кнопка + горячая клавиша).
Разделы, которые еще не готовы, **не показываются** в меню (а не висят «скоро»).

### 4.2 Карточка проблемы / возможности

- Заголовок, сумма ₽/мес, вид (проблема / возможность), процесс, уверенность («высокая — 2 инвентаризации, полные данные»).
- График: мой ресторан vs среднее по сети vs норма, по неделям / между инвентаризациями.
- «Почему так» — объяснение ИИ и вероятные причины (списком, без обвинений).
- «Что сделать» — шаги из плейбука и ожидаемый эффект.
- «Доказательства» — таблица строк (накладные, списания, инвентаризации) с раскрытием.
- Кнопки: **Беру в работу** · **Не согласен** (с причиной) · **Обсудить с ИИ**.

### 4.4 Загрузка данных

Перетащить файл → система определяет источник и тип («iiko · Инвентаризация, R02, 01.10») → предпросмотр
маппинга колонок (подтвердить один раз) → отчет проверки (ошибки / предупреждения) → «Загрузить».
Ниже — таблица свежести: ресторан × источник (r_keeper продажи, iiko склад, ERP закупки) с датой последних данных.

### 4.5 Чат (панель)

Контекст сверху («Обсуждаем: перерасход сыра, R01»), подсказки вопросов, ответы с таблицей/графиком
и ссылкой «откуда цифра», кнопки «создать задачу» (черновик с подтверждением).

## 5. Состояния

| Состояние | Как выглядит |
|-----------|--------------|
| Нет данных | Пояснение + кнопка «Загрузить данные» + что именно нужно ([09](09-data-requirements.md)) |
| Мало данных | Блок виден, но с пометкой и подсказкой («нужна 2-я инвентаризация») |
| Загрузка | Скелетоны, не спиннер на весь экран |
| Ошибка | Понятный текст + повторить; без технических сообщений |
| Все хорошо | Позитивный пустой экран («Проблем выше нормы не найдено. Посмотрите возможности») |

## 6. Визуальная система

- shadcn/ui + Tailwind, один нейтральный фон, акценты по смыслу: красный — потери, зеленый — возможности/норма,
  янтарный — внимание. Цвет никогда не единственный носитель смысла (плюс иконка/текст).
- Числа — моноширинные цифры (tabular-nums), выравнивание по правому краю в таблицах.
- Минимальный размер текста 12px, контраст AA.
- Графики — ECharts, единая палитра.

## 7. Прототип (этап 1.5)

Кликабельный прототип в `frontend/` на демонстрационных данных (`frontend/src/mock/`), вход — реальный (роли и изоляция
работают через API). Что важно:

- **Типы моков — контракт API.** `mock/types.ts` описывает данные, которые экраны ждут от аналитики (находки, KPI,
  процессы, эксперименты, задачи, свежесть данных). Этапы 3–7 должны отдавать эти структуры — тогда экраны подключаются без переделки.
- **Итоги считаются кодом** (`mock/selectors.ts`): «на столе», статусы процессов, средние по сети — как в будущем расчетном слое.
- **Правила доступа повторяют API:** директор видит только свой ресторан и среднее по сети; чужие находки и разделы УК
  открываются как «не найдено»; ассистент отказывается сравнивать с другими точками.
- **Чат — сценарный:** отвечает на фиксированный набор тем цифрами из моков; в рабочей версии его заменит Claude с инструментами.
- Взаимодействия (взять в работу, поставить задачу, утвердить эксперимент, отметить задачу) хранятся в памяти страницы и сбрасываются при обновлении.
