# 01. Доменная модель

Модель проектируется «как у учетных систем» (близко к понятиям iiko), чтобы будущие API-интеграции
ложились на те же таблицы, что и импорт из Excel.

## Карта сущностей

```
Tenant (франчайзер / УК)
 ├── Restaurant ──── RestaurantGroup (регион, формат, «кластер» для сравнения)
 ├── User ── RoleAssignment(role, scope: tenant | restaurant[])
 │
 ├── Справочники (мастер-данные)
 │    ├── Product            — ингредиент / товар / полуфабрикат (единая номенклатура сети)
 │    ├── NameAlias          — как товар / блюдо / поставщик называется в другой системе: на всю сеть или для одного ресторана
 │    ├── ProductCategory    — овощи, мясо, молочка… (у категории — допуски потерь)
 │    ├── Unit + UnitConversion (кг↔г, шт↔кг для конкретного товара)
 │    ├── Supplier
 │    ├── MenuItem           — блюдо (продаваемая позиция)
 │    └── Recipe (ТТК) ── RecipeVersion(valid_from, valid_to) ── RecipeLine(product|semi, брутто, нетто, % потерь)
 │
 ├── Операции (факты, все с restaurant_id и датой)
 │    ├── Sale               — продажи блюд: дата, блюдо, кол-во, выручка, скидка
 │    ├── Receipt            — приходная накладная: поставщик, товар, кол-во, цена, сумма, НДС
 │    ├── Transfer           — перемещение между точками / складами
 │    ├── WriteOff           — списание: товар, кол-во, причина (порча, питание персонала, проработка…)
 │    ├── Production         — производство п/ф (если ведется)
 │    ├── InventoryCount     — инвентаризация: дата, товар, учетный остаток, фактический остаток
 │    └── StockSnapshot      — остатки на дату (если выгружаются отдельно)
 │
 ├── Аналитика (результаты расчетов, пересчитываемые)
 │    ├── ConsumptionFact    — витрина: ресторан × товар × период: теория, факт, списания, расхождение
 │    ├── CostPrice          — себестоимость товара на дату (средневзвешенная)
 │    ├── Forecast           — прогноз продаж/потребности/остатка
 │    └── MetricValue        — посчитанные метрики (фудкост %, индексы и т.д.)
 │
 └── Цикл улучшений
      ├── Finding (инсайт)   — вид (problem: теряем | opportunity: можем заработать), тип, объект, метрика,
      │                        значение, бенчмарк, эффект ₽/мес, уверенность, процесс, статус
      ├── Hypothesis         — что изменить, ожидаемый эффект, метрика успеха, ссылка на Finding
      ├── Experiment (проверка) — тестовая и контрольная группы, период, статус proposed → running → completed | rejected;
      │                        решение УК о запуске (кто, когда); результат: вердикт, ₽/мес, интервал, вывод
      ├── Task               — задача в ресторане: что сделать, срок, чек-лист, кто поставил (УК / директор),
      │                        отчет директора, результат (TaskOutcome)
      └── TaskOutcome        — сработало / не сработало / считаем, ₽/мес, как посчитано; пишет только аналитика
```

Сквозные служебные сущности: `ImportBatch` (каждая загрузка), `AuditLog` (кто что сделал), `AiRun`
(каждый вызов LLM: промпт-версия, входы, выход, стоимость).

## Ключевые правила (инварианты)

1. **Мультиарендность.** Каждая запись имеет `tenant_id`. Каждая операционная запись — `restaurant_id`.
   Доступ ограничивается и в коде, и в БД (Row-Level Security) — см. [03](03-architecture.md).
2. **Версионность ТТК.** Расчет теории за дату использует версию ТТК, действовавшую на эту дату.
   Изменение ТТК задним числом не переписывает историю, а создает новую версию.
3. **Полуфабрикаты раскрываются рекурсивно.** Блюдо → п/ф → п/ф → сырье. Проверка на циклы при импорте.
4. **Единицы измерения.** Внутри системы все количества хранятся в базовой единице товара (кг, л, шт).
   Конверсии хранятся явно; неизвестная конверсия = ошибка качества данных, а не молчаливая подстановка.
5. **Единая номенклатура.** Разные названия одного товара в разных ресторанах сводятся к одному `Product`
   через `NameAlias` (подтверждает человек один раз). Без этого сравнение ресторанов невозможно (см. риски).
6. **Происхождение данных.** Каждая операционная запись знает свой `import_batch_id` и `source`
   (`xls`, позже `iiko_api`). Повторная загрузка того же периода заменяет данные этого периода/ресторана
   идемпотентно, а не дублирует.
7. **Деньги** — `Decimal`/`NUMERIC(14,2)`, валюта на уровне тенанта. Выручка хранится с и без НДС/скидок.
8. **Результаты аналитики воспроизводимы:** у `Finding` хранится версия алгоритма, период и ссылки на
   исходные данные (evidence), чтобы любой инсайт можно было «раскрыть» до строк накладных.

## Жизненный цикл Finding

```
new → in_work (поставлена задача) → in_experiment (запущена проверка) → resolved
  ↘ dismissed (аналитика пересчитала: проблемы больше нет)
```

Оспаривания находок директором нет — директора исполняют ([ADR 0006](adr/0006-tasks-execution-and-traceability.md)).
Для экранов этап работы выводится из находки, ее задач и проверки (`app/insights/work.py`):
«Новые» → «Делаем» (есть задачи) → «Проверяем» (идет проверка) → «Есть результат» (подтвержден эффект или проверка
завершена). Просрочка задачи не хранится — выводится из срока и текущей даты.

## Жизненный цикл Task

```
assigned → in_progress → done (отчет директора обязателен; результат = «считаем»)
                              → результат: confirmed (₽/мес) | not_confirmed — пишет аналитика после пересчета
```

- УК ставит задачу ресторану; задача по сетевой находке уходит всем ресторанам. Директор берет задачи только себе.
- Выполняет задачу только директор своего ресторана; УК задачи не выполняет.
- Эффект задачи проверки хранится у проверки, задачи получают только вердикт — сумма не считается дважды.
