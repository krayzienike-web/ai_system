# 12. Аналитический движок: логика, модель, параметры

Документ описывает, **как именно** SousChef AI находит проблемы: какие данные берет, как считает, по каким
правилам решает, что это находка, и как человек ее проверяет. Что считать — в [02](02-analytics-spec.md);
здесь — как это реализовано и где менять. Любое изменение логики сначала вносится сюда (и обсуждается во вкладке
«Движок» в штабе проекта), потом в код и тесты.

Код: `backend/app/analytics/`. Версия алгоритма: `engine-1` (пишется в каждую находку).

## Принципы

1. **Все цифры считает код.** Движок — детерминированные функции на Python с unit-тестами. Нейросеть (Claude)
   в расчетах и решениях движка **не участвует** — ни сейчас, ни после этапа 5. Позже она будет только
   объяснять уже посчитанные находки в чате и в сводке директору ([08](08-director-digest-and-chat.md)).
2. **Человек проверяет.** Пока движок новый, каждая находка проходит ручную проверку управляющей компанией,
   прежде чем ее увидит директор (см. «Проверка находок»).
3. **Консервативно.** Эффект считается до ориентира (норма или медиана сети), а не до идеала. Лучше пропустить
   мелкую проблему, чем показать ложную.
4. **Объяснимо.** У каждой находки есть доказательства (`evidence`): исходные числа по периодам, порог,
   ориентир. Экран проверки пересчитывает их из загруженных строк.

## Конвейер

```
загруженные файлы → факты (facts.py) → метрики (costs, usage, m1…) → детекторы → черновики находок
  → находки (engine.py, по ключу) → проверка УК (review) → директор видит подтвержденные
```

- **Запуск:** кнопка «Пересчитать находки» на экране «Проверка находок» (администратор УК), `POST /api/analytics/run`,
  команда `python -m app.cli analyze`; после загрузки демо-сети — автоматически. Автоматический пересчет после
  каждой публикации файла — этап 4 (фоновая задача).
- **Права:** запускает только администратор УК; движок видит все рестораны сети (RLS с охватом всей сети).
- **Идемпотентность:** у каждой находки есть ключ `модуль:ресторан:объект` (например `M1:R01:P01`, `M1:net:P11`).
  Повторный запуск на тех же данных обновляет числа и тексты, сохраняя статус, задачи, проверки и решение
  проверяющего. Находка, которую движок больше не видит, удаляется, только если по ней еще ничего не делали
  (статус «новая», нет задач и проверок, не отклонена). Отклоненные остаются как запись решения.
- Находки модулей, которые текущая версия не запускает, движок не трогает.

## Общие понятия

### Инвентаризации и периоды
- Остаток по инвентаризации — **на конец дня** инвентаризации. Период между инвентаризациями `d0` и `d1`
  включает дни `d0+1 … d1`: движения дня `d0` уже учтены в остатке `d0`.
- Период короче **14 дней** не оценивается (`M1_MIN_THEORY_DAYS`): слишком мало продаж для вывода.
- Товар оценивается в периоде, только если он есть в **обеих** инвентаризациях.

### Себестоимость (`costs.py`)
- **Средневзвешенная цена закупки** товара в ресторане за период: Σ сумм / Σ количества по накладным.
- Цена **с НДС**, как в накладной (выручка в r_keeper тоже с НДС). Вопрос E2 ниже.
- Если в периоде закупок не было: средняя по закупкам ресторана за 90 дней до конца периода, затем средняя по сети
  за период. Нет закупок нигде — сумма не оценивается, находка показывается без рублей.

### Расход по техкартам (`usage.py`)
- `T = Σ продажи блюда × норма брутто товара на порцию` по версии техкарты, действующей в день продажи.
- Полуфабрикаты раскрываются в сырье рекурсивно (соус → томаты, масло). Циклы запрещены при загрузке.
- Блюда без техкарты в расход не попадают (их показывает модуль качества данных M7).

### Эффект в рублях
- Всегда **₽ в месяц**: сумма за период × 30 / число дней периода.

## M1. Исполнение техкарт (реализован)

**Вопрос:** расходуется ли товара больше, чем положено по техкартам, сверх допустимых потерь?

**Формула** для ресторана, товара и периода между инвентаризациями:
- фактический расход `A = остаток на начало + приход + перемещения в ресторан − перемещения из ресторана − остаток на конец`;
- необъяснимый расход `U = A − T − W`, где `W` — оформленные списания;
- `U% = U / T`; ориентир `B` — допуск категории товара (нормы сети) или, если сравнение с сетью включено,
  большее из допуска и медианы `U%` по сети в том же периоде.

**Правило «техкарта устарела» (находка на всю сеть, только для УК):**
- в последнем периоде не менее **75%** ресторанов (`M1_NET_SHARE`) выше допуска;
- и медиана сети выше допуска не менее чем на **2 п.п.** (`M1_NET_EXCESS`).
- Рублей нет: деньги не теряются, но фудкост и потери по сети считаются неверно. Действие — проработка и новая
  техкарта.

**Правило «перерасход в ресторане»** (последний период по товару):
1. `U%` выше ориентира `B`;
2. если в сети **8 и более** ресторанов (`NETWORK_Z_MIN_RESTAURANTS`): ресторан выбивается из сети —
   robust z-score `(U% − медиана) / (1,4826 × MAD) > 2` (`M1_Z`), MAD не меньше 0,5 п.п. (`M1_Z_FLOOR`);
   в пилоте из 3 ресторанов z-score не используется — только допуск;
3. эффект `(U% − B) × T × цена` не меньше **3 000 ₽ в месяц** (`M1_MATERIALITY_RUB_MONTH`).
- Если по товару сработало правило «техкарта устарела», ориентир для ресторанов — медиана сети: показываются
  только те, кто хуже остальных и на фоне ошибки техкарты.
- В заголовке — динамика по всем периодам; «растет», если каждый период хуже предыдущего.

**Как считается «выбивается из сети» (robust z-score), на примере моцареллы 04.08–01.10:**
1. Доли необъяснимого расхода по ресторанам за один период: у 11 ресторанов 1,6–3%, у R01 — 11,4%.
2. Типичный ресторан — медиана: 2,0%. Медиана, а не среднее, чтобы один плохой ресторан ее не сдвигал.
3. Обычный разброс — медиана отклонений от медианы × 1,4826 (MAD, приведенный к стандартному отклонению): ≈ 0,2%,
   но не меньше 0,5 п.п. (`M1_Z_FLOOR`), чтобы почти одинаковая сеть не превращала мелочь в тревогу.
4. z = (11,4 − 2,0) / 0,5 ≈ 19. Порог 2: отклонение больше двух обычных разбросов случайно бывает примерно в 5% случаев.

**Уверенность:** высокая, если периодов два и больше; средняя — если один.

**Не делает (пока):**
- экономию (`U < 0`, недовложение — риск качества) не показывает; она же бывает при пересорте (это M4). Вопрос E3.
- не учитывает частичные инвентаризации и инвентаризации по местам хранения.

**Проверено на демо-сети:** находит все три заложенные аномалии M1 (моцарелла R01, лосось R03, картофель фри по сети)
и ничего лишнего ([11](11-demo-network.md), тест `tests/test_analytics.py`).

## M2. Фудкост блюд (реализован)

**Вопрос:** какие блюда стоят дороже в приготовлении, чем позволяет целевой фудкост сети, и сколько можно
заработать, пересмотрев цену?

**Расчет:**
- себестоимость порции = Σ ингредиентов по техкарте (полуфабрикаты раскрыты) × цена закупки;
- цена закупки — средневзвешенная **по всей сети за последние 4 недели** (`M2_WINDOW_DAYS`): цены в меню едины
  для сети, поэтому и находка — на всю сеть, для управляющей компании;
- фудкост блюда = себестоимость порции / цена в меню (обе с НДС);
- цель — из «Норм и настроек»: по сети или по категории меню.

**Находка (возможность), если одновременно:**
1. фудкост блюда выше цели;
2. потенциал не меньше **3 000 ₽ в месяц** (`M2_MATERIALITY_RUB_MONTH`).

**Потенциал** = (фудкост − цель) × выручка блюда по сети × **0,5** (`M2_KEEP`) в ₽ в месяц. Половина — консервативно:
после подорожания часть гостей закажет другое блюдо.

**Причина в находке:** сравнение с тем же окном квартал назад (`M2_COMPARE_DAYS` = 91 день) — на сколько выросла
себестоимость порции и какой ингредиент подорожал сильнее всего. **Рекомендованная цена** — себестоимость / цель,
округленная вверх до 10 ₽.

**Не делает (пока):** фактический фудкост ресторана (по инвентаризациям) и разрыв «факт − теория» — это показатели
для дашбордов этапа 4, а деньги по ним уже показывает M1; меню-инжиниринг — в бэклоге.

**Проверено на демо-сети:** находит заложенную ситуацию — лосось +40% с 01.09, «Лосось на гриле» 31,9% при цели 30%,
рекомендуемая цена 1 480 ₽ вместо 1 390 ₽. Остальные блюда (фудкост 9–24%) находок не дают.

## M3. Закупочные цены (реализован)

**Вопрос:** где ресторан платит поставщикам больше, чем остальные рестораны сети за тот же товар?

**Расчет** за последние **8 недель** закупок в сети (`M3_WINDOW_DAYS`):
- средняя цена ресторана = сумма по накладным / количество (взвешенная по объему, с НДС);
- типичная цена сети = медиана средних цен **других** ресторанов (ресторан не сравнивается сам с собой);
- переплата = (средняя цена − типичная цена сети) × количество, в ₽ в месяц.

**Находка, если одновременно:**
1. цена выше типичной цены сети больше чем на **5%** (`M3_OVERPAY`);
2. при 8 и более ресторанах — цена выбивается из сети: robust z-score > 2, разброс не меньше 1% (`M3_Z_FLOOR`);
3. переплата не меньше **3 000 ₽ в месяц** (`M3_MATERIALITY_RUB_MONTH`).
- Товар оценивается, если у ресторана не меньше **2 закупок** в окне (`M3_MIN_RECEIPTS`) и в сравнении есть еще
  хотя бы 2 ресторана.

**Объяснение в находке** — по основному поставщику ресторана (с наибольшей суммой закупок в окне):
- он не основной ни у одного другого ресторана → «Закупка у дорогого поставщика» (часто срочные закупки);
- тот же поставщик, что у других → «Поставщик продает дороже, чем другим» (повод для единой цены сети).
- «С какого числа» — начало последней непрерывной серии закупок дороже типичной цены сети более чем на 2,5%,
  по всей истории закупок.

**Цена выше договорной** (находка на всю сеть, для УК) — когда загружены договорные цены (файл «Договорные цены»):
накладные поставщика за 8 недель сравниваются с договорной ценой, действовавшей в день накладной; накладные дороже
договора больше чем на 1% (`M3_CONTRACT_TOLERANCE`, округления) дают переплату по ресторанам. Находка, если переплата
не меньше 3 000 ₽ в месяц.

**Цена выросла по всей сети** (находка на всю сеть, для УК) — когда договорных цен на товар нет: средняя цена сети
за 4 недели (`M3_NET_WINDOW_DAYS`) против тех же 4 недель квартал назад (`M3_NET_COMPARE_DAYS`). Находка, если рост
больше **10%** (`M3_NET_GROWTH`) и сумма сверх прежней цены не меньше 3 000 ₽ в месяц. В находке — основной поставщик,
с какого числа и сколько ресторанов закупают. Если договорная цена загружена, вместо этой находки срабатывает
«Цена выше договорной».

**Номенклатура 1С:ERP и iiko.** В ERP один товар iiko часто заведен несколькими позициями — по одной на поставщика
(«Помидоры 1», «Помидоры 2»). Выгрузка сервиса «Синхронизация ЕРП–iiko» загружается файлом «Синхронизация 1С:ERP —
iiko»: каждая позиция ERP становится запомненным соответствием товару iiko на всю сеть. Накладные из ERP после этого
сводятся к одному товару, и M3 сравнивает цены разных поставщиков на один и тот же товар (Q13).

**Не делает (пока):** скачки цены относительно собственной истории ресторана, возможность «лучшая цена сети»
(opportunity) — в бэклоге «Новые виды находок».

**Проверено на демо-сети:** находит обе заложенные аномалии (говядина R02 у срочного поставщика с 27.07 — 8 393 ₽/мес,
сливки R05 у того же поставщика на 14% дороже — 5 006 ₽/мес) и ничего лишнего.

## Проверка находок

- Новая находка движка получает статус проверки **«на проверке»**. Директор ее не видит: это обеспечивает
  сама база (RLS), а не только интерфейс. Сетевые находки директор не видит никогда.
- Проверяют администратор и аналитик УК на экране **«Проверка находок»**:
  - **сверка с данными** — находка пересчитывается заново из загруженных строк отдельным, более простым кодом;
    расхождение с тем, что посчитал движок, видно как непройденная проверка (данные изменились после пересчета
    или ошибка в движке);
  - **расчет по шагам** — каждое слагаемое формулы с исходными строками и именем файла, из которого они пришли;
  - **сработавшие правила** — значение, порог, выполнено или нет;
  - **динамика по периодам** и подсказки, как читать находку.
- Вердикт: **подтвердить** (находку увидит директор) или **отклонить** с причиной — ошибка в данных, ошибка
  в логике расчета, не проблема (известно, согласовано, сезонно), другое. Для «ошибки в логике» и «другого»
  нужен комментарий: по нему правим движок. Решение можно вернуть на проверку.
- Повторный пересчет решения не сбрасывает. Отклоненная находка не всплывает снова.
- **Но если новые данные заметно изменили находку** — эффект изменился больше чем на `REVIEW_RECHECK_CHANGE`
  (25 %), сменился ресторан или вид находки, — она снова уходит на проверку с пометкой «эффект изменился с … до …».
  Директор не видит сумму, которую никто не подтверждал; отклоненная, но сильно выросшая находка получает второй
  взгляд.
- Пока находка не проверена, по ней нельзя поставить задачу или запустить проверку изменений, и она не входит
  в отчет руководителю. Причину отклонения и комментарий проверяющего видит только УК.
- Ручную проверку можно выключить в «Нормах и настройках» — тогда новые находки сразу попадают директорам.
- Находки, заведенные вручную, проверку не проходят. Если движок находит ту же проблему, он берет такую находку
  под себя и считает ее проверенной.
- Статистика решений (сколько подтверждено, отклонено и почему) — материал для настройки порогов.
- **Путь находки трассируем**: найдено движком (дата, модуль) → проверено (дата, кто) → в находках. Цепочка
  видна в карточке проверки (со ссылкой «Открыть в находках») и в блоке «Найдено движком и проверено» в начале
  раздела «Находки» (со ссылкой на расчет и проверку). API: `GET /api/findings` отдает `found_on`,
  `review_status`, `reviewed_on`, `reviewed_by_name`.

## Параметры

**Нормы сети** — задает администратор УК в «Нормах и настройках» (`app/norms`):

| Параметр | Значение по умолчанию | Где используется |
|----------|-----------------------|------------------|
| Целевой фудкост | 30%, можно по категориям меню | M2 |
| Допустимые потери сверх техкарты | овощи и зелень 3%, мясо, птица, рыба 2%, сыры и молочные 1,5%, бакалея и напитки 1%, прочее 2% | M1 |
| Справочник причин списания | стандартный, до получения регламента (Q7) | M5, M4 |
| Ручная проверка находок | включена | все модули |

**Параметры движка** — значения по умолчанию в `app/analytics/params.py` (меняются через этот документ и штаб).
Сеть может переопределить их в «Нормах и настройках» → «Параметры движка» (администратор УК, по модулям; значения
в человеческих единицах, хранятся в `norm_settings.engine_params`, API `GET/PUT /api/settings/engine`); пустое
значение возвращает умолчание. Движок и сверка читают параметры сети при каждом пересчете.

| Параметр | Значение | Смысл |
|----------|----------|-------|
| `REVIEW_RECHECK_CHANGE` | 25 % | проверенная находка снова на проверке, если эффект изменился больше |
| `M1_MATERIALITY_RUB_MONTH` | 3 000 ₽/мес | меньшие потери не стоят внимания директора |
| `M1_Z` | 2 | насколько ресторан должен отличаться от сети |
| `M1_Z_FLOOR` | 0,5 п.п. | минимальный разброс для z-score |
| `NETWORK_Z_MIN_RESTAURANTS` | 8 | меньше — сеть слишком мала для статистики |

## Как менять логику

1. Предложение — во вкладке «Движок» штаба проекта (или вопрос/отклонение находки с причиной «ошибка в логике»).
2. Изменение описывается в этом документе: что, почему, на каких данных проверено.
3. Код и тест: сначала тест на демо-сети или на примере, который показал проблему; затем код.
4. Растет версия алгоритма (`ALGORITHM_VERSION`), пересчет обновляет находки.
