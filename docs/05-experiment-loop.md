# 05. Цикл «инсайт → гипотеза → эксперимент → эффект»

Это ядро продукта и главный аргумент для инвестора: система не просто показывает графики, а превращает
данные в проверенные деньги.

## Шаги

1. **Finding.** Детектор находит проблему, считает эффект в ₽/мес и уверенность. Narrator объясняет.
   Аналитик УК подтверждает находку на «Проверке находок», и она попадает в «Ждут решения» → «Решить по
   находке». УК решает: сразу поставить задачу директору или сначала проверить изменение (шаги 2–5). Директор
   видит находку только с задачей ([ADR 0009](adr/0009-findings-reach-directors-through-hq-decision.md)).
2. **Гипотеза.** ИИ предлагает (или аналитик УК создает) гипотезу по шаблону:
   *«Если в ресторанах {группа} сделать {изменение}, то {метрика} изменится на {ожидание} за {срок},
   что даст {₽/мес}»*. Источник изменений — меры из находки (поле «что сделать» движка); отдельная библиотека плейбуков —
   в бэклоге до пилота (например: «контрольное взвешивание
   порций на раздаче», «еженедельная инвентаризация топ-20 позиций», «перевод закупки на поставщика S»,
   «обучение по ТТК + фото-стандарт блюда», «уменьшение партии заказа»).
3. **Дизайн эксперимента.** Система подбирает:
   - **тестовую группу** — рестораны, где делаем изменение (обычно с проблемой);
   - **контрольную группу** — похожие рестораны без изменения (подбор по формату, выручке, baseline-метрике);
   - baseline-период (4–8 недель до) и тестовый период (2–6 недель);
   - метрику успеха и минимальный детектируемый эффект.
4. **Запуск.** Руководитель УК смотрит карточку (эффект, риски, группы, задачи) → запускает / правит / отклоняет.
   Запуск ставит задачи директорам тестовых ресторанов (`POST /api/checks/{id}/launch`).
5. **Задачи.** Директорам тестовых ресторанов создаются задачи: что сделать, срок, чек-лист, требуемое подтверждение
   (комментарий, фото, файл). Напоминания. УК видит статус исполнения.
6. **Замер.** По окончании (и промежуточно) — оценка методом **difference-in-differences**:
   `Эффект = (Тест_после − Тест_до) − (Контроль_после − Контроль_до)`,
   доверительный интервал — bootstrap по дням/ресторанам. Результат в ₽/мес.
7. **Решение.** ИИ формулирует вывод; УК решает: тиражировать на сеть (с прогнозом эффекта), продлить, отказаться.
   Подтвержденный эффект копится в счетчике **«Сэкономлено с помощью AI»**.

## Замер (как считает код, этап 7)

Замер — детерминированная функция (`analytics/measure.py`) над загруженными строками; ни одно число не вводит человек и
не пишет модель. Запускается после каждого пересчета движка.

**Метрика — по виду находки, из которой сделана проверка** (товар, кассир — из находки):

| Находка | Метрика (за период) | Лучше, если | ₽ в месяц |
|---------|---------------------|-------------|-----------|
| M1 перерасход | закуплено товара / расход по техкартам | ниже | −Δ × расход по техкартам в месяц × цена |
| M5 списания, M6 затоваривание | списано товара / расход по техкартам (по дням ровнее, чем закупки) | ниже | −Δ × расход по техкартам в месяц × цена |
| M3 цена | средняя цена закупки, ₽ за единицу | ниже | −Δ × закуплено в месяц |
| M8 скидки | скидки / продажи до скидок | ниже | −Δ × продажи до скидок в месяц |
| M8 удаления | удалено после пречека, ₽ в день | ниже | −Δ × 30 |

Цена и объемы для перевода в рубли — тестового ресторана за период до проверки; месяц — 30 дней с продажами (не
календарных: при короткой истории иначе сумма занижается). Находки других видов (инвентаризации, данные, меню,
сетевые) проверкой не замеряются: предложение такой проверки отклоняется — по ним сразу задача.

**Периоды.** До — столько же недель перед стартом, сколько длится проверка, но не меньше 4. После — со старта до
конца проверки. Дизайн, метрика, группы и периоды фиксируются при предложении и задним числом не меняются. Запустили
позже даты старта — весь период сдвигается на день запуска (длина та же), период «до» пересчитывается.

**Эффект** = (тест после − тест до) − (контроль после − контроль до), в единицах метрики, затем в ₽ в месяц.
Контроль — сумма строк контрольной группы: похожих ресторанов (дизайн 1) или других товаров той же категории в том же
ресторане (дизайн 2); в дизайне 3 контроля нет — просто до и после, без поправки («слабое доказательство»). Для
кассира (M8) контроль — рестораны сравнения целиком или другие кассиры того же ресторана. Для цены (M3) дизайн 2 не
предлагается: цены разных товаров между собой не сравнить. Дизайн доступен, если у него есть с чем сравнивать.

**Интервал** — 95%, bootstrap по дням: 1 000 повторов, дни каждой из четырех клеток (тест/контроль × до/после)
выбираются с возвращением; зерно — из id проверки, поэтому один и тот же замер дает одни и те же числа.

**Вывод:**
- **«Подтвержден»** — весь интервал в ₽ выше нуля;
- **«Направление верное, но не значимо»** — эффект выше нуля, интервал задевает ноль;
- **«Не подтвержден»** — эффект не выше нуля.
- Если в части повторов bootstrap не нашлось ни одного дня с расходом (меньше 95% повторов уцелело) — пометка «мало
  данных», вывод не выше «не значимо».

Подтвержденный эффект идет в «Сэкономлено с помощью AI».

**Ход и итог.** Пока проверка идет — промежуточный замер «за N дней» (вывод не пишется; меньше 14 дней — «судить
рано»). Срок прошел и продажи с закупками загружены до конца проверки — итог, статус «завершена». Данных не хватает —
«ждем данных по DD.MM»; контрольный ресторан, не загрузивший данные за 14 дней после конца, исключается с пометкой.
Сравнить к концу не с чем — проверка закрывается как «не значимо» с причиной («замерить нечего»), а не висит.

**Прогноз тиражирования** (у подтвержденной) — по каждому другому ресторану: его «резерв» (уровень метрики, для
перерасхода — только сверх техкарты) × доля улучшения, которую замер приписал мере (эффект с поправкой на контроль /
уровень теста до), в его объемах и ценах. Для цены не считается.

**Минимальный заметный эффект** — в черновике, для каждого дизайна и срока (2, 4, 6 недель): насколько должна
сдвинуться метрика, чтобы замер это увидел (2,8 стандартной ошибки эффекта; ошибка — тем же bootstrap на периоде до
проверки, разделенном пополам; половина дисперсии — от периода «после», она уменьшается с длиной как √(половина /
длина)). «Рекомендуем» — только дизайн, который за выбранный срок увидит ожидаемый эффект. Если ни один не увидит —
мастер предупреждает: итог скорее всего «не значимо», лучше срок длиннее или сразу задача. В проверку записывается
порог для выбранных ресторанов, срока и дат предложения; если запуск позже, период сдвигается, а порог остается
оценкой на момент предложения (он про мощность замера, а не про итог; решение после ревью этапа 7).

**Гипотеза** — по шаблону черновика: «Если в ресторане «…» {мера}, «{метрика}» приблизится к {цели} за {срок} — это
+{₽} в месяц»; мастер подставляет выбранные меру и срок, в проверку записывается та же формулировка.

## Эксперименты в пилоте на 3 ресторанах

С тремя точками классическая схема «группа ресторанов против группы» почти не работает. Поэтому система поддерживает
три дизайна и предлагает подходящий:

1. **Ресторан против ресторанов**: 1 тестовый + 2 контрольных, difference-in-differences по дневным данным.
2. **Контроль внутри ресторана**: изменение применяется к части позиций или смен, остальные — контроль
   (например, контрольное взвешивание только для мясных блюд; эффект — разница динамики мясных и остальных позиций).
   Работает даже в одном ресторане и дает больше наблюдений.
3. **До/после** — когда мера вводится везде сразу или сравнить не с чем: изменение показателя без контроля, без
   поправки на сезонность (поправку отложили — решение ревью этапа 7), с пометкой «слабое доказательство».

## Честность замера

- В франшизе ресторанов мало (в пилоте — 3) → статистическая мощность ограничена. Система явно показывает:
  «эффект подтвержден / направление верное, но не значимо / не подтвержден» — без подгонки.
- Если контрольной группы нет (например, мера для всех) — до/после без поправки, с пометкой «слабое доказательство»
  и в итоге, и на экране проверки.
- Фиксация дизайна до старта (метрика и период не меняются задним числом).

## Статусы

Как в коде (решение 09.11.2026: отдельные «planned», «measuring», «rolled_out» не нужны — их смысл уже есть):

- `Experiment: proposed → running → completed (confirmed | inconclusive | rejected)`; `proposed → rejected` — УК
  отклонила предложение. Тиражирование — дата `rollout_on` у подтвержденной проверки. «Идет замер» — проверка
  `running` с промежуточным замером; срок прошел, а данных нет — `running` с текстом «ждем данных по DD.MM».
- «Повторить дольше» — новая проверка `proposed` с тем же дизайном и сроком длиннее (до 12 недель), прежняя остается
  как была; доступно при «не значимо» и «не подтвержден» (эффект мог не проявиться, если меру выполняли непостоянно),
  пока по находке нет открытой проверки. Карточка находки ведет на открытую проверку (повтор), а не на старую.
- `Task: assigned → in_progress → done` (итог задачи проверки — из замера) | просрочена (срок прошел).
