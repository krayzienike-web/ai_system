# 05. Цикл «инсайт → гипотеза → эксперимент → эффект»

Это ядро продукта и главный аргумент для инвестора: система не просто показывает графики, а превращает
данные в проверенные деньги.

## Шаги

1. **Finding.** Детектор находит проблему, считает эффект в ₽/мес и уверенность. Narrator объясняет.
2. **Гипотеза.** ИИ предлагает (или аналитик УК создает) гипотезу по шаблону:
   *«Если в ресторанах {группа} сделать {изменение}, то {метрика} изменится на {ожидание} за {срок},
   что даст {₽/мес}»*. Источник изменений — библиотека плейбуков (например: «контрольное взвешивание
   порций на раздаче», «еженедельная инвентаризация топ-20 позиций», «перевод закупки на поставщика S»,
   «обучение по ТТК + фото-стандарт блюда», «уменьшение партии заказа»).
3. **Дизайн эксперимента.** Система подбирает:
   - **тестовую группу** — рестораны, где делаем изменение (обычно с проблемой);
   - **контрольную группу** — похожие рестораны без изменения (подбор по формату, выручке, baseline-метрике);
   - baseline-период (4–8 недель до) и тестовый период (2–6 недель);
   - метрику успеха и минимальный детектируемый эффект.
4. **Запуск.** Руководитель УК смотрит карточку (эффект, риски, группы, задачи) → запускает / правит / отклоняет.
   Запуск ставит задачи директорам тестовых ресторанов (`POST /api/checks/{id}/launch`).
5. **Задачи.** Директорам тестовых ресторанов создаются задачи: что сделать, срок, чек-лист, требуемое подтверждение
   (комментарий, фото, файл). Напоминания. УК видит статус исполнения.
6. **Замер.** По окончании (и промежуточно) — оценка методом **difference-in-differences**:
   `Эффект = (Тест_после − Тест_до) − (Контроль_после − Контроль_до)`,
   доверительный интервал — bootstrap по дням/ресторанам. Результат в ₽/мес.
7. **Решение.** ИИ формулирует вывод; УК решает: тиражировать на сеть (с прогнозом эффекта), продлить, отказаться.
   Подтвержденный эффект копится в счетчике **«Сэкономлено с помощью AI»**.

## Эксперименты в пилоте на 3 ресторанах

С тремя точками классическая схема «группа ресторанов против группы» почти не работает. Поэтому система поддерживает
три дизайна и предлагает подходящий:

1. **Ресторан против ресторанов**: 1 тестовый + 2 контрольных, difference-in-differences по дневным данным.
2. **Контроль внутри ресторана**: изменение применяется к части позиций или смен, остальные — контроль
   (например, контрольное взвешивание только для мясных блюд; эффект — разница динамики мясных и остальных позиций).
   Работает даже в одном ресторане и дает больше наблюдений.
3. **До/после с поправкой на сезонность и динамику других точек** — когда мера вводится везде сразу (пометка «слабое доказательство»).

## Честность замера

- В франшизе ресторанов мало (в пилоте — 3) → статистическая мощность ограничена. Система явно показывает:
  «эффект подтвержден / направление верное, но не значимо / не подтвержден» — без подгонки.
- Если контрольной группы нет (например, мера для всех) — до/после с поправкой на сезонность, с пометкой «слабое доказательство».
- Фиксация дизайна до старта (метрика и период не меняются задним числом).

## Статусы

`Hypothesis: draft → proposed → approved | rejected`
`Experiment: planned → running → measuring → completed (confirmed | inconclusive | rejected) → rolled_out`
`Task: assigned → in_progress → done (подтверждено) | overdue | rejected_by_hq`
