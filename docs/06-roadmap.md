# 06. Роадмап MVP

Один план. Каждый этап заканчивается работающим, показываемым результатом (вертикальный срез), а не «слоем».
Оценки — ориентир для одного full-stack разработчика с ИИ-ассистентом.

| Этап | Содержание | Критерий готовности | Оценка |
|------|-----------|---------------------|--------|
| **0. Проработка** | Видение, доменная модель, аналитика, архитектура, требования к данным, ADR | Документы согласованы, открытые вопросы [07](07-risks-questions-ideas.md) закрыты | сейчас |

Типы моков = контракт API для этапов 3–7 (`frontend/src/mock/types.ts`) | Сценарии обеих ролей проходятся кликами; показ 2–3 директорам пилота | 1 нед |

| **5.5. Решение УК по находке** | По [ADR 0009](adr/0009-findings-reach-directors-through-hq-decision.md): подтвержденная находка → «Ждут решения» → УК ставит задачу директору или предлагает проверку; директор видит находку только с задачей; «Беру в работу» у директора убирается | Директор не видит находку без задачи ни на одном экране, в сводке и в чате; каждая подтвержденная находка без решения — в «Ждут решения» | 2–3 дня |
| **6.5. Движок: добор** | Новые находки: скачок цены к своей истории (M3), меню-инжиниринг (M2), связанные находки, скидки и удаления из чеков, затоваривание (M6), цены и неполные пересчеты, оценка качества данных (M7); загрузка новых выгрузок: «Остатки на дату» (iiko), «Удаления и отмены» (r_keeper), кассир в продажах | Каждая находка ловит заложенную в демо аномалию и ничего лишнего; новые выгрузки загружаются через «Данные»; все описано в docs/12 и docs/09 | 1–1,5 нед |
| **7. Цикл экспериментов** | Гипотезы, три дизайна (вкл. контроль внутри ресторана), запуск, задачи, замер | Полный цикл на демо-данных | 1,5 нед |
| **8. Пилот и демо** | Профили источников под реальные выгрузки iiko / r_keeper / 1С:ERP, загрузка 3 пилотных ресторанов, сценарий для инвестора, стенд в облаке | Реальные данные пилота загружены; демо за 10 мин без сбоев | 1,5 нед |

Итого ≈ 15 недель (с этапами 6.1 и 6.5). Показ инвестору — по готовности MVP.

Реальные выгрузки можно подключить раньше: как только они появятся, профили источников под них делаются
параллельно с этапами 3–5 — это снижает риск этапа 8.

## Ход этапа 2

(сеть / ресторан), экран запомненных соответствий с пересчетом файлов. Полуфабрикаты в ТТК (вложенность, проверка
циклов, разворот блюда в сырье на дату) и перемещения между ресторанами. Остается: профили источников — после
реальных выгрузок (Q5). Этап 2 по сути закрыт; следующий — аналитический движок (этап 3).

## Порядок разработки внутри этапа

1. Тесты/фикстуры на демо-данных → 2. backend-сервис → 3. API (OpenAPI) → 4. сгенерированный клиент → 5. UI → 6. e2e.

## После MVP

AI-автозаказ → API-интеграции iiko / r_keeper / 1С → Telegram-бот директора → модуль «Финансы (P&L)» →
AI HR (графики, текучесть, ФОТ) → маркетинг/гость (отзывы, CRM) → контроль качества (чек-листы, фото-аудит).

## Этап 5. Чат с ассистентом — план (28.10.2026)

Ключа Claude API пока нет (Q12): все строим и проверяем на заглушке модели, модель подключается одной
переменной окружения, когда ключ появится. Сервера для демо-стенда тоже пока нет (Q17): готовим развертывание
и проверяем его локально.

1. **Подготовка из архитектурного ревью:**
   - один путь чтения находки «как ее видит этот пользователь»;
   - короткая сессия с изоляцией (RLS) на каждый вызов инструмента;
   - тест изоляции, который обходит все маршруты;
   - import-linter с границами модулей.
2. **Шлюз к модели** (`app/ai/gateway`, ADR 0005):
   - заглушка модели для тестов;
   - журнал вызовов (`ai_runs`);
   - промпты — файлы с версией;
   - бюджет запросов на пользователя.
3. **Инструменты чата.** Тонкие обертки над сервисами: находки, показатели, сравнение с сетью, цены закупок,
   документы. У каждого — схема входа и выхода и тест изоляции.
4. **Чат:**
   - история диалогов;
   - ответ потоком (SSE);
   - проверка каждого числа в ответе по результатам инструментов;
   - «Обсудить с ИИ» из карточки находки.
5. **Проверочный набор вопросов (eval)** на демо-сети с ответами, которые считает код. В CI он идет на заглушке,
   с ключом — на модели. Критерий этапа: ≥ 90 % верных ответов и ни одной утечки чужих данных.
6. **Демо-стенд** (ADR 0007, изменение 28.10.2026):
   - рабочий `docker-compose`, nginx, HTTPS;
   - ночной сброс демо-сети;
   - выкладка, когда будет сервер (Q17).

**Сделано к 28.10.2026:** пункты 1–5. Пункт 6 подготовлен (`deploy/`):

## Этап 5.5. ИИ-помощник аналитика — план (28.10.2026)

По [ADR 0008](adr/0008-ai-proposes-code-verifies-human-approves.md): ИИ предлагает, код проверяет, человек
утверждает. Ключа модели пока нет (Q12): все строим и проверяем на заглушке, как этап 5. Эталон для оценки — 16
заложенных аномалий демо-сети ([docs/11](11-demo-network.md)): у каждой известна настоящая причина.

1. **Общая основа:**
   - структурированный ответ модели по JSON-схеме через шлюз;
   - хранилище предложений ИИ (`ai_suggestions`): что предложено, на чем основано, версия промпта, решение человека;
   - пометка «Предложение ИИ» в интерфейсе, кнопки «Принять» и «Отклонить»;
   - статистика «ИИ предлагал / человек решил».
2. **«Почему так» и «что делать» по находке.** Код собирает контекст:
   - что менялось рядом: поставщики, цены, техкарты, меню;
   - причины списаний, даты инвентаризаций;
   - проблемы данных того же ресторана и периода;
   - похожие прошлые находки и итоги их проверок;
   - правила сети (например, когда меняются цены в меню).

   ИИ выбирает до трех причин из фиксированного списка категорий. Для каждой пишет, как проверить ее на месте, и
   предлагает шаги. Цифры сверяются с контекстом. Директору — только по своим находкам.
3. **Предпроверка находок для аналитика.** До ручной проверки код помечает, на что посмотреть:
   - разовый всплеск;
   - смена поставщика;
   - проблемы выгрузки в том же периоде;
   - мало данных.

   ИИ готовит черновик вердикта с обоснованием. Вердикт ставит человек.
4. **Поиск новых типов находок.** ИИ просматривает агрегаты (не сырые строки) и предлагает закономерности. Каждая
   ссылается на строку агрегата, и код проверяет ее цифры. Аналитик принимает идею — она уходит в «Идеи находок»,
   а правило пишется кодом с тестом.
5. **Новые форматы выгрузок.** Незнакомые колонки размечаются сначала по словарю синонимов, потом ИИ (по заголовкам
   и образцу строк) с объяснением. Разметку проверяет валидация импорта на самом файле. Человек подтверждает ее
   один раз, она сохраняется как профиль источника, и следующие файлы грузятся сами.
6. **Проверочные наборы** для каждой функции на демо-сети. В CI — на заглушках, с ключом — на модели. Критерии:
   - причины заложенных аномалий в топ-3 ≥ 80 %;
   - разметка незнакомого формата верна после одного подтверждения;
   - ни одной цифры ИИ без сверки.

**Сделано к 02.11.2026:** пункты 1–5, проверочный набор «почему так» (`make eval-hypotheses`). Модель везде
заглушка. Осталось:
- замер критериев на настоящей модели (Q12): причина в топ-3, разметка с первого подтверждения;

## Этап 6. AI-сводка — план (02.11.2026)

Основа — docs/08, часть 1. Сводка — это экран «Моя неделя», ставший еженедельным выпуском: собранный, сохраненный,

2. **Выпуск сводки (`digests`).** Хранится вход, текст, версия промпта и дата. Выпуск идемпотентен: одна неделя

## Этап 6.5. Движок: добор — план (03.11.2026)

Решение заказчика 03.11.2026: доделать находки, которые были «в плане», и сразу добавить загрузку выгрузок, которых
им не хватает, — чтобы на пилоте их оставалось только загрузить. В демо-сеть заложить по аномалии на каждую новую
находку. На пилоте (этап 8) остаются то, что требует реальных файлов: частичные инвентаризации и места хранения (M1,
Q5), примеры синхронизации 1С:ERP — iiko и договорных цен (M3, Q13, Q14), справочник причин списания сети (M5).

**Новые выгрузки (импорт, docs/09):**
1. **«Остатки на дату» (iiko)** — ежедневный остаток товара по ресторану; срок годности — из номенклатуры. Нужна
   для затоваривания и уточняет риск дефицита (M6) между инвентаризациями.
2. **«Удаления и отмены» (r_keeper)** — удаленные позиции и отмененные чеки: дата и время, чек, блюдо, сумма,
   кассир, до или после печати чека, причина.
3. **Кассир в продажах** — необязательная колонка в шаблоне «Продажи»: скидки по кассирам.

**Находки:**
1. **M3. Скачок цены к своей истории** — ресторан платит за товар заметно больше, чем обычно платил сам.
2. **M2. Меню-инжиниринг** — матрица «популярность × маржа»: популярное блюдо с низкой маржой (пересмотреть цену
   или техкарту), непопулярное с высокой (продвигать). Возможность в ₽.
3. **Связанные находки** (docs/12) — находки с общей причиной (товар, поставщик, даты) показываются одной историей:
   «цена выросла → фудкост вырос → блюдо стало невыгодным»; сумма не задваивается.
4. **Скидки и удаления из чеков** — доля скидок, удалений после печати и отмен у ресторана и кассира заметно выше
   сети. Без выгрузки удалений — только скидки.
5. **M6. Затоваривание** — запас больше, чем успеют потратить до конца срока годности. Только по выгрузке
   «Остатки на дату».
6. **M7. Цены и пересчеты** — нулевые и аномальные цены в накладных; инвентаризация без части обычно
   пересчитываемых товаров.
7. **M7. Оценка качества данных ресторана (0–100)** — на обзоре ресторана и в сводке; низкая оценка снижает
   уверенность находок ресторана.

**Документы, штаб, тесты:** docs/09 (новые шаблоны), docs/12 (логика находок) и раздел «Движок» в штабе, новые
пороги в «Параметрах движка», реестр тестов, пересчет демо и запись прототипа.


**Сделано к 06.11.2026:** все пункты. Каждая новая находка ловит заложенную в демо-сеть аномалию и ничего лишнего, ее

## Этап 7. Цикл экспериментов — план (09.11.2026)

Уже есть (этапы 4–6.1): из находки система готовит проверку (мера из находки, ресторан, рестораны сравнения по
выручке, срок), аналитик предлагает, администратор УК запускает — директору ставится задача; подтвержденную проверку
тиражируют на сеть. **Нет главного — замера:** результаты проверок в демо-сети записаны вручную (`demo/showcase.py`),
ни одна строка кода их не считает. Этап делает замер и честный вывод.

**Шаги:**
1. **Замер (код, docs/05).** Для каждого вида находки — дневная метрика из загруженных строк и перевод в ₽/мес:
   - перерасход M1 — закупки товара к расходу по техкартам;
   - списания M5 — списания товара к расходу по техкартам;
   - цена M3 — средняя цена закупки;
   - касса M8 — доля скидок и удаления после пречека;
   - затоваривание M6 — как списания (решение ревью: остаток на дату слишком редкий для дневного ряда).
   Замер:
   - эффект — разница разниц (тест после − до) − (контроль после − до);
   - интервал — bootstrap по дням, с фиксированным зерном, чтобы один и тот же результат повторялся;
   - вывод — «подтвержден / направление верное, но не значимо / не подтвержден».
   Запускается после каждого пересчета движка: идет проверка — промежуточный замер, срок прошел и данные загружены —
   итог. Дизайн фиксируется при запуске и задним числом не меняется.
2. **Три дизайна.** Система предлагает подходящий:
   - ресторан против похожих ресторанов (есть);
   - контроль внутри ресторана: мера на части позиций, остальные — контроль;
   - до/после без поправки — «слабое доказательство».
   В черновике — минимальный эффект, который замер сможет заметить, для 2, 4 и 6 недель.
3. **Гипотеза по шаблону** «Если в {где} сделать {что}, {метрика} изменится на {сколько} за {срок} — {₽/мес}» и
   меры — из находки (отдельная библиотека плейбуков — в бэклоге).
4. **Решение по итогу:** вывод словами по правилам (числа — только из замера), тиражировать с прогнозом, продлить,
   отказаться.
5. **Демо-сеть:** замер вместо записанных результатов. Заложить эффект под проверки:
   - новый случай в прошлом — списания томатов R04 до середины сентября, проверка «малые партии» их снижает, итог
     «подтвержден», тиражирование;
   - хлеб R07 — без эффекта, итог «не подтвержден» или «не значим»;
   - моцарелла R01 — идет, промежуточный замер.
   Сегодняшние заложенные находки не меняются.
6. **Экраны:** дизайн и группы на карточке проверки, ход замера, честный ярлык итога, минимальный эффект.
7. **Документы, штаб, тесты, пересчет демо, код-ревью, тестировщик.**

**Сделано к 10.11.2026:** все пункты. Результаты проверок демо-сети посчитаны кодом: томаты R04 — «подтвержден»,
