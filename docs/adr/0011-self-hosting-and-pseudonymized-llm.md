# ADR 0011. Свой сервер и обезличенные данные для внешнего ИИ

**Статус:** предложено (требование заказчика, 19.11.2026); реализация не начата.

## Контекст
Заказчик требует для службы информационной безопасности:
- система разворачивается на своем сервере компании (не в чужом облаке);
- в интернет не уходят связки «день — ресторан — сотрудник» и другие привязки к реальным объектам;
- с внешней моделью ИИ общаемся только обезличенными идентификаторами, а связка ID с реальными объектами
  строится бэкендом на своем сервере.

Сейчас ([ADR 0005](0005-llm-provider-abstraction.md)) в Claude API уходят агрегированные данные с названиями ресторанов,
товаров и блюд (тексты записок агентов, чат, сводки). Персональные данные не передаются, но названия и даты — да.

## Решение (предложение)
1. **Хостинг.** Целевая поставка — на сервере заказчика (Docker Compose: Postgres, Redis, бэкенд, фронтенд).
   Наружу — только HTTPS-запросы к Claude API.
2. **Обезличивание в шлюзе ИИ** (`backend/app/ai/gateway`). Перед отправкой шлюз заменяет названия ресторанов,
   товаров, блюд, поставщиков, сотрудников на стабильные псевдонимы (`R-17`, `P-204`, `S-3`, `E-12`); таблица
   соответствий хранится только в своей базе и не уходит наружу. Даты сдвигаются или заменяются на относительные
   («неделя N»), где это не мешает смыслу.
3. **Обратная подстановка.** Ответ модели приходит с псевдонимами; шлюз подставляет реальные названия до показа
   пользователю. Проверка чисел (ADR 0008) работает как сейчас.
4. **Тест.** Для каждого вызова модели — тест, что в запросе нет названий из справочников и ФИО.

## Последствия
- Слайд «Информационная безопасность» в презентации функционала описывает эту целевую схему.
- Нужен этап в роадмапе: псевдонимизация шлюза, тесты, прогон eval на обезличенных промптах (качество текстов
  может просесть — модель не видит, что «P-204» — это лосось; часть подсказок придется давать категориями).
- Открытый вопрос к заказчику: допустимы ли в запросе категории товаров и типы ресторанов (без названий).
